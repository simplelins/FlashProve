# Anthropic FlashProve 项目现状评估

## 一、总体判断

FlashProve 的现状可概括为：**技术跑通、性能堪忧、停止演进**。

它在秘密权重大模型的计算完整性证明上实现了关键突破，通过 PCD 折叠式证明和批量权重指纹共享，显著降低了大规模推理证明的边际成本，并在透明设置下提供了抗量子的零知识保证。但当前原型仅覆盖 1024 token 窗口、整数 MoE 模型和贪心解码，证明成本是普通推理的 70–95 倍，且缺少 KV Cache 状态转移、浮点一致性、随机采样一致性以及端到端实现级形式化保证。它解决了“模型版本是否被替换”的核验问题，但无法解决模型真实性锚定、输出语义正确性、长序列连续证明和实时部署成本问题。现阶段更适合离线审计与合同核验，距离连续在线推理证明和生产级安全部署仍有多项独立技术难题待解。

**特别提醒：本项目是 AI 推进的研究原型，仓库已不再维护、不接受外部贡献，后续人工跟进难度极大。** 任何团队若想 fork 继续推进，需从零承接整套自研证明系统、C++ 验证器和 Lean 形式化证明，工程迁移与持续维护成本极高。

## 二、技术可行性已获验证

### 2.1 应用场景

解决模型服务商为了降本替换劣质模型，或为了刷榜替换更强模型等信任缺失问题。核心诉求是：用户无需获取模型权重，即可验证回答确实来自服务商承诺的模型。

### 2.2 技术路线

- **证明系统类型**：基于 zkIOP + 折叠式证明系统（PCD 风格），辅以后量子抗量子哈希证明路线。并非经典 zkSNARK（不依赖配对假设的可信初始化），采用透明设置（transparent setup）。
- **核心机制**：离线生成模型权重指纹（Fingerprint），后续每次推理生成局部证明；通过递归折叠（PCD）将多个请求的权重指纹检查聚合，大幅降低边际证明成本。
- **指纹生成成本**：针对 Llama 4 Maverick 400B MoE，单张 H100 耗时约 39 分钟完成权重哈希（SHA-256/Poseidon）。此为一次性离线成本，可摊薄至千万次请求，单次请求边际成本极低。

### 2.3 验证数据（基于 Llama 4 Maverick 400B MoE）

| 指标         | 数值                | 说明                                                                           |
| ------------ | ------------------- | ------------------------------------------------------------------------------ |
| 证明生成吞吐 | 110 tokens/s        | 单张 H100 + 24 CPU 线程，批量处理 24 个请求（每请求 1024 token），223 秒内完成 |
| 证明大小     | 约 18.78MB          | 1024 token 窗口对应单份证明                                                    |
| 验证耗时     | 约 17 秒            | 普通 CPU（24 线程）完成验证                                                    |
| 模型架构     | MoE，约 400B 总参数 | 单 token 激活约 17B 参数，4-bit 量化权重，整数计算                             |

> 注意：110 tok/s 是“证明吞吐”而非“证明延迟”。单 token 从输入到证明落地的端到端延迟远高于 1/110 秒，且证明为批量后处理（batch amortization）产物，不适用于对延迟敏感的在线服务。

## 三、工程落地存在硬性瓶颈

### 3.1 算力成本极高

生成证明的 GPU 时间消耗是普通推理（vLLM）的 **70–95 倍**。在现有商业环境下，这属于不可承受的成本，尤其对于高吞吐推理服务。

### 3.2 上下文窗口极短

目前仅支持 **1024 token** 上下文窗口，距离真实业务需求（万级以上）相去甚远。复杂对话、长文档理解、多轮 Agent 任务均无法覆盖。

### 3.3 模型结构受限

- **仅适用于 MoE 架构**：实验对象为 Llama 4 Maverick，约 400B 总参数，MoE 架构。非 MoE 模型未验证。
- **整数量化及贪心解码**：FlashProve 证明的是经过严格定义的整数模型计算，而非任意浮点推理过程。不适用于目前广泛使用的浮点模型或随机采样生成。
- **浮点偏差风险**：4-bit 整数量化+贪心解码会引入分布偏移，整数模型输出与原始浮点模型输出不一定一致。FlashProve 证明的是“整数模型算对了”，不是“浮点模型算对了”。若服务商对量化后的模型做对抗性微调，证明照样成立，但业务语义可能完全偏离原始模型——这本质上是一种模型替换攻击，FlashProve 无法检测。

### 3.4 证明语义不完整

- **每份实验请求 1024-token 只检查一个指定的输出 token**，并非对完整输出序列生成严格证明。
- **KV Cache 状态转移没有证明**：证明对象是“给定输入窗口 → 指定输出 token”的局部计算，不保证 KV Cache 在 token 间的一致性转移，无法证明“第 N+1 个 token 的证明依赖第 N 个 token 的正确状态”。这是长序列连续证明的核心缺口。
- **未覆盖随机采样与长序列生成的全部计算一致性问题**。
- **未实现任意大模型浮点推理的完全证明**。

### 3.5 安全保证的形式化缺口

- **协议层形式化**：Lean 对完备性、可靠性和零知识进行了机器可检查证明。
- **实现层未形式化**：C++ 验证器（快速验证器）未经过 Fiat-Crypto 等自动化证明生成，也未经过高强度模糊测试和侧信道审计。协议证明和实现证明是两回事，存在实现级安全风险。

### 3.6 信任锚问题

FlashProve 只能证明“输出来自某个已知指纹的模型”，但指纹本身如何绑定到真实模型权重，它无法解决。需要外部信任锚（如模型权重的可信登记、签名体系、TEE 辅助的权重加载证明）配合。没有这个，FlashProve 防的是“服务商偷偷换模型”，防不了“服务商用假指纹骗你”。它解决的是**模型版本一致性**，不是**模型真实性**。

### 3.7 项目状态与后续跟进难度

- **仓库明确标注不再维护、不接受外部贡献**，暂未形成成熟的生产级组件。
- **本项目是 AI 推进的研究原型**，整套证明系统、C++ 验证器和 Lean 形式化证明均由 AI 主导生成，工程结构复杂、内部依赖耦合度高。
- **后续人工跟进难度极大**：任何团队若想 fork 继续推进，需从零承接整套自研证明系统，缺乏官方文档和社区支持，工程迁移与持续维护成本极高。

## 四、适用性边界

| 场景                | 适用性    | 说明                          |
| ------------------- | --------- | ----------------------------- |

| 连续在线推理证明    | ❌ 不适合 | 上下文窗口短、KV Cache 无证明 |

## 六、工作进展及王诚建议

借助AI经过反复迭代，用一个自定义小模型完成了FlashProve在 sm_89 (RTX 4090 D) 上的移植，能跑通，未与H100做测试对比

王诚借助AI分析给出的建议如下：

1. flashprove东西做的很琐碎，只能按他算法逻辑一个单元一个单元算；做一个sumcheck单元和一个hash commit单元，先能接进去跑起来再说；
2. 这种baseline的设计，建议买点好的AI模型token，让AI投入先去实现，完了再分析下一步的工作
