## B1 · sumcheck 协议（2 课：一课理论一课实现）

### 目标
完整掌握 sumcheck——包括数学证明、误差界、批处理与 ZK 变体。这是整个 FlashProve 归约链的
发动机。

### 讲义
**陈述**：给定 m 变量多项式 f（各变量次数 d_i），证明 Σ_{x∈{0,1}^m} f(x) = v。验证者只拿到
oracle 访问权（最终要查 f 在一个随机点的值——在 FlashProve 里这个"查询"被传递给下一层）。

**协议**（i 从 1 到 m）：
1. 证明者发单变量多项式 g_i(X_i) = Σ_{x_{i+1},…,x_m∈{0,1}} f(r_1,…,r_{i−1}, X_i, x_{i+1},…,x_m)；
2. 验证者检查 deg(g_i) ≤ d_i、g_i(0)+g_i(1) = 前一轮声称的值（第 0 轮 = v）；
3. 验证者抽 r_i ← E，把 g_i(r_i) 作为下一轮的声称值；
4. 最后一轮验证者自己算 f(r_1,…,r_m) 与最后消息比对（oracle 查询）。

**Soundness**：若 v 不对，则每一轮证明者"赌对"一个随机挑战的概率 ≤ d_i/|E|，总误差
≤ Σ_i d_i / |E|。对 multilinear（d_i=1）：m/|E|。证明的关键引理：若某轮 g_i "诚实"了，之后
永远诚实不了地回头（一旦在某个前缀上 Σ 已经错了，后面每轮的检查要么继续错，要么必须赌
新的随机点）。自己把 Thaler Ch4 的归纳论证抄一遍——这是本课程要求你手推的第三个证明。

**批处理 sumcheck**：多个声称 Σ f_j = v_j，验证者抽随机权重 α_j，证明 Σ α_j f_j = Σ α_j v_j
一次跑完——FlashProve 把一段的所有方程"batched into one claim"用的就是这个。

**ZK / 掩码 sumcheck**：轮消息 g_i 泄露 f 的信息。掩码法：证明者加一条随机多项式 h_i
（满足 h_i(0)=h_i(1)=0，使检查等式仍成立），发 g_i + h_i。FlashProve 用的是 **masked
sumcheck**：blocks 的接口在 `iop/hp.h`，但**实现不在 blocks 里**——blocks/README 明说：
"Inside a request's sub-proofs cp_prove and cp_verify run implementations of their own of the
masked sum-check, the look-ups and the range check, so this folder's tests say nothing about
those"。这在读代码时极其重要：`prover/` 与 `verifier/src/` 各有一份实现，测试对齐它们。

**最后一步的去向**：FlashProve 里 sumcheck 结束时验证者**不去查** f(r)——这个"线性声称"
被并入待办清单，由下一段的 proximity test 统一结算（协议 §5.3 末句："Random masks hide the
values sent along the way"；§5.4 末句："the folds carry it along, and the verifier checks it at
the end against what was sent"）。这是理解 C3 的钥匙。

### 在 FlashProve 中的位置
- 协议 §5.3："A sumcheck reduces a claim about a sum of millions of terms to a claim about the
  polynomials that define the terms, at one random point."
- 验证端实现：`verifier/src/vf_sumcheck_psc.h`（per-segment sumcheck）、`vf_sumcheck_token.h`、
  `vf_sumcheck_attention.h`、`vf_sumcheck_receive.h`。

### 作业
1. 实现 toy sumcheck：f(x₁,x₂,x₃) 由 2³ 表给出（MLP）。验证：诚实路径接受；把表改一位后
   以假 v 跑 1000 次，统计作弊成功率 ≈ m/|E|。
2. 加掩码变体：每轮发 g_i + h_i，验证验证者检查仍通过、且轮消息分布与假陈述无关。
3. 接到 A4 的 FS 链上，得到非交互 sumcheck 文件。
4. 读 `vf_sumcheck_psc.h` 的函数签名，对着 toy 代码找对应物（只读签名，不必读懂实现）。

### 自测与答案要点
- **误差为什么是 Σd_i/|E|？** 每轮 a ≠ b 的两个 deg≤d 多项式在 ≤d 个点相等；挑战随机 ⇒
  赌中概率 ≤ d/|E|；轮间独立。
- **验证者要读多少数据？** 每轮一条 deg≤d 的单变量消息（d+1 个数）+ 最终一次 f(r) 查询；
  总通信 O(Σ d_i · log|E|)。
- **FlashProve 为什么用 masked sumcheck？** 轮消息含 trace 信息，会泄中间值（= 权重的函数）。

## B2 · GKR 与"FlashProve 为什么不用它"（1 课）

### 目标
掌握 GKR 的结构，理解两种 zkML 路线（GKR 逐层 vs trace 承诺+通用归约）的取舍——这直接
对应你之后要做的 DeepProve 对比。

### 讲义
**GKR**：对**分层**算术电路，逐层把"层 l 的输出线性组合= 某值"归约到层 l−1。核心是对布线
谓词跑 sumcheck：V_{l+1}(u) = Σ_{v} M(u,v)·V_l(v)，其中 M 是布线矩阵。挑战向量一路向下
传播，验证者只需电路输入层的求值。代价：证明者每层做两次 sumcheck（u 和 v 各一）。

**DeepProve 路线**（据其论文与你的笔记核对）：对网络的每一层跑 GKR/sumcheck，非线性用
lookup，量化到定点。**不承诺权重**（权重是公开输入或以其他方式处理），也不承诺中间 trace
——GKR 的挑战链本身就是"验证者眼中的计算轨迹"。

**FlashProve 路线**：模型按**段（segment）**切分，每段把 trace（中间值表）**承诺**下来，用
通用 sumcheck + lookup 把"这段算得对"归约成线性声称；段与段之间通过**折叠承诺**传递——
"prover folds each segment's commitments into one short commitment and carries it into the next
segment, so it need not keep the whole trace"（协议 §6.3 first chain 段）。权重以 holographic
方式预先承诺（权重表），全程零知识。

**取舍表**（讨论课主题）：

| | GKR 逐层（DeepProve） | trace 承诺+归约（FlashProve） |
|---|---|---|
| 权重 | 不承诺/公开 | holographic 承诺 + 隐藏 |
| 中间值 | 不承诺（挑战链承载） | 逐段承诺、折叠传递 |
| 零知识 | 需额外处理 | 掩码内建 |
| 证明者内存 | 需逐层计算 | 折叠后只需短承诺 |
| 绑定权重 | 无需 | 需要（磨损/OOD/码定理） |

### 作业
1. 实现 2 层 toy GKR（布线谓词是恒等+一个置换），对比 trace 承诺法在同一电路上的消息数。
2. 写 300 字：如果 DeepProve 要加"权重承诺+隐藏"，GKR 框架里缺哪些原语？（答案要点：承诺
   层、proximity test、OOD、掩码 sumcheck、查询预算管理——即 FlashProve 的大部分贡献。）

### 自测与答案要点
- **GKR 验证者为什么不用承诺中间层？** 挑战 r_l 传到下一层，验证者只需要输入层的求值
  （或经子协议提供）。
- **FlashProve 为什么逐段折叠？** 单卡放不下全部 trace；折叠后"携带"的是短承诺，权重从主机
  内存流式读入。

### 资料
Thaler Ch6；DeepProve 论文（`/home/lww/project/06_zkp/deep-prove/docs/zkml_bootcamp/deepprove.pdf`
及你的笔记）；协议 §6.3。

## B3 · IOP：形式化框架（1 课）

### 目标
掌握 IOP 定义、round-by-round soundness、知识健全性与**提取器**——后者是理解 Lean 定理
"false = false at the weights that a fixed extractor reads off"的唯一途径。

### 讲义
**IOP**：验证者对证明者的每条消息只有 **oracle 访问**（读任意位置），不是全文读取。它是
信息论对象——先设计 IOP，再用 Merkle + Fiat–Shamir 编译成"文件 + 哈希"的论证系统。

**Round-by-round (RBR) soundness**：定义一个状态函数，协议每轮后状态要么"接受"要么在坏
事件集里；每轮坏事件概率 ≤ ε_i，则总误差 ≤ Σ ε_i。协议 §7 的论证正是这个结构："Each round
gives it only a small chance of that, and in a single try its overall chance is at most the sum
of the rounds' chances."（"Everything a challenge tests is fixed before the challenge exists" =
FS 链保证 RBR 适用。）

**知识健全性与提取器**：强化的 soundness——作弊者让验证者接受 ⇒ 存在提取器（一个数学
函数，**不要求可计算**）从作弊者的哈希查询记录中"读出"一个 witness。Lean 定理的措辞
"false means false at the weights that a fixed extractor reads off the commitment and the
committer's hash queries, which need not be the provider's"（what-is-proved.md）就是这个概念：
提取器甚至不假设作弊者就是提供商。注意两个推论：
- 提取器给出"无"时，每次接受都算失败（"where it gives none, every accepted proof counts as a
  failure"）；
- "知道权重"不被声明——声明的是提取函数的输出关系。

**Holographic IOP**：验证者可以在协议开始前就拿到对部分数据（权重表）的承诺——FlashProve
的权重表正是 holographic 承诺：commit 阶段编码全部权重，之后每个证明只通过"test on the
table"引用它。

**本协议的三个 IOP**（GAPS.md 术语表，权威）：
| 文件 | IOP 名 | 诚实方 | soundness 引理 |
|---|---|---|---|
| key file | offline IOP | key file's prover | `keySound` |
| leaf/copy file | link IOP | link proof's prover | `entrySound` |
| proof file | online IOP | request's prover | `proofSound` |
共七条 hash chain：key file 3 条 + copy file 1 条 + proof file 3 条（first/shared/second）。

### 作业
1. 写出 RBR soundness 的形式定义并证明 ⇒ 蕴含普通 soundness（一页纸）。
2. 把协议 §7"Why a false claim should be rejected"一节抄写一遍，给每一句标注它对应 B 阶段
   哪个原语（hash trees=A4、proximity+OOD=B4/B6、range=B5、test on the table=C3）。
3. 读 GAPS.md 术语表（1–2 小时），自建术语卡：index / instance / extractor / commitment ID /
   copy / OOD sample / query bound / gate / in scope。

### 自测与答案要点
- **提取器不可计算为什么没关系？** 定理只需要"存在一个函数把（承诺,查询记录）映到权重"，
  安全论证是概率性的，不要求算法实现。
- **为什么把 N 个证明放一起提交误差是 N 倍？** 每个证明的接受事件是"对同一个提取出的
  权重"而言的坏事件，联合界直接相加（what-is-proved: "N proofs handed in at once … cost N
  times that error, taken at the whole list's hash queries"）。

### 资料
Thaler Ch7/Ch8；GAPS.md 术语节；what-is-proved.md。

## B4 · proximity test 与 code switching（2 课）

### 目标
掌握从 FRI 到本协议所用测试（Chiesa–Fenzi–Weissenberg，ePrint 2026/391）的演进，理解
fold → code switching → base case 三步结构与它顺带证明线性声称的机制。

### 讲义
**问题**：验证者只看到少数几列（几条 Merkle 路径）。如果承诺的数据**不是**某个向量的合法
编码，打开的列毫无意义——验证者检查的一切都建在沙子上。proximity test 证明：承诺的表
**接近某条码字**（与"某个向量的编码"距离 < 固定分数）。

**FRI（背景）**：递归折半——对承诺的多项式行用随机因子折叠，次数减半，重复到底；验证者
在随机位置对照新旧承诺。DEEP-FRI 加了 out-of-domain 点使界更紧。

**本协议的测试**（协议 §5.4，这是权威描述，背下来）：
1. **fold**：证明者把所有行用随机因子折成一行，提交（"combines the rows, with random factors,
   into one row (a fold)"）；
2. **code switching**：把折叠行切开成短行，在**更短的码**下提交（"splits that row into shorter
   rows and commits to them under a shorter code"），验证者在随机位置对照新旧承诺
   （"checks the new commitment against the old one at random positions"）；
3. 重复直到短到可以**掩码形式直接发送**（"until what remains is short enough to send in masked
   form"）；
4. **顺带证明线性声称**："they are batched into one claim, the folds carry it along, and the
   verifier checks it at the end against what was sent"——所有"承诺向量某线性组合=某值"的
   声称打包成一条，随折叠传递，最后清算。这就是 B1 说的"sumcheck 的最终声称由 proximity
   test 结算"。

**距离与 list decoding**：测试允许的距离到 Johnson 半径 ⇒ 可能多个码字都"接近"⇒ 需要 OOD
采样钉死唯一消息（B6）。

**工程形态**：blocks/iop 的块清单（blocks/README）——`fold.h`、`cs.h`（code switch）、
`base_case.h`、`foldeq.h`、`batt.h`（batching）、`lin.h`（linear claims）、`link.h`（两表链接）、
`member.h` 等。每块 = 一个头文件三件套 `plan_x` / `x_prove` / `x_verify`（blocks 规则 4）。
哪些块对应协议的哪些步，是你 B4 的读码任务（我给出推测，你验证）。

### 在 FlashProve 中的位置
- PUBLISHED-WORKS.md："The paper that this protocol builds on" = ePrint 2026/391（有差异清单）。
- 一次批处理中：**shared chain + 每请求的 second chain 合称 "the test on the table"**（协议
  §6.3）；承诺阶段对 anchor 跑一次同样的测试（one-time test）；leaf table 的 link proof（C2）
  是两表版本的 proximity test。

### 作业
1. 实现 toy FRI：RS(16,4)，验证诚实接受、构造一个"远离所有码字"的假承诺并演示被拒。
2. 实现 toy code switching：长码 [16,4] → 短码 [8,2]，对照随机位置。
3. 读 `blocks/iop/` 的 fold.h / cs.h / base_case.h 头注释，验证或推翻我的块映射表，写 200 字

4. 精读协议 §5.4 + §6.3 shared chain 的五步（fold → 开列 → 线性声称 → 派生共享向量 →
   proximity 证明），画完整消息流图。

### 自测与答案要点
- **为什么折叠后还要 code switching？** 折叠降低"对象数"，切短码降低"码长"，两者结合把
  验证者最终要看的数据压到常数级。
- **线性声称怎么"被折叠携带"？** 折叠是线性的：行向量折叠后，原来关于各行的线性声称
  变成关于折叠行的同一形式声称，系数组合方式不变。

（STARK 部分）。

## B5 · lookup argument（1 课）

### 目标
掌握 lookup 的两类主流构造；理解 FlashProve 用 lookup 做的三件事：承诺期的范围证明、每段
的 "smallness" 范围检查、以及模型查找表（SiLU/sigmoid/softmax）的执行。

### 讲义
**声称**：承诺向量 w 的每个元素 ∈ 公开表 T。逐元素打开代价太高，需要 argument。

**Plookup**（Gabizon–Williamson–Ciobotaru）：把 w 与 T 排序合并，证明相邻差分要么是 T 的
差分要么为 0——排序本身要用协议证明（多一跳）。**logUp**（Haböck–Papini）：对每个表元素
t 引入重数列 m_t，声称 Σ_{x∈w} 1/(x−β) = Σ_t m_t/(t−β)；把倒数求和转成 sumcheck 友好的形式，
重数用随机挑战打包。FlashProve 风格是后者（sumcheck 生态）。

**FlashProve 的三处使用**：
1. **承诺期范围证明**（协议 §6.1 步骤 2，注意这叫 range proof）："Lookups show that the digits
   are in fixed small ranges, and that the weights assembled from them are too. For the
   embedding, however, only the digits are checked."——没有这步，承诺者可以用巨大的域元素，
   让"模 p 成立"的方程在整数意义下不成立（作弊空间）。
2. **每段 range check（"smallness"）**（协议 §6.3 first chain 段，注意这**不是**上面的 range
   proof）：trace 承诺后，验证者抽因子 ∈ {−1,0,1}，lookup 数字位证明"trace 值与这些因子的
   组合"是小的 ⇒（除去小概率）值本身在更松的界内也小 ⇒ 结合模型数值大小条件，"模 p 的
   方程"同时也是"整数上的方程"。`cp_verify` 检查这些条件（no-overflow conditions）；技术
   报告有引理连接两者，但"cp_verify 的测试正是引理所指"只知自读码、未被证明。
3. **模型查找表**：整数模型（docs/model.md）的非线性函数全部走表——SiLU 表按 key=256·gc+g0
   查、softmax 表 EX、sigmoid 表 Sig，四个公开表（rha/rne 定义的浮点步骤序列）各有
   BLAKE2b 摘要记在参数文件里（tsilu/tsig/trope/texp）。证明"查表执行正确"就是 lookup
   argument 的工作。

### 在 FlashProve 中的位置
- 验证端：`vf_lookup_argument.h`、`vf_lookup_helpers.h`、`vf_norm_digit_rows.h`（数字位行的
  规范化）；
- blocks 侧接口：`iop/lkp.h`。

### 作业
1. 实现 toy logUp 范围检查：承诺 8 个值，证明全部 ∈ [0,256)。实现重数计数版本并跑通。
2. 作弊实验：让一个值 =300，跑 1000 次统计失败率；解释失败率来自哪里（重数和不为零 ⇒
   多项式不为零 ⇒ Schwartz–Zippel）。
3. 读 `docs/model.md` §4（五个公开表与四个摘要），回答：为什么表要"摘要进参数文件"而不是
   现算？（答案要点：摘要把表钉进承诺 ID 覆盖的范围；验证者不必重新计算浮点步骤序列，
   且避免不同库舍入差异——model.md §4 的 C(689,1) 例子。）

### 自测与答案要点
- **range proof 与 range check 区别？** 前者在承诺期对数字位（防域元素溢出作弊），后者在
   每段对 trace（防"模 p 成立但整数不成立"）；名字相近、位置和目的不同。
- **{−1,0,1} 因子的作用？** 多个值的组合保持在可 lookup 的小范围内，同时 Schwartz–Zippel
   保证组合小 ⇒ 原值小（松界）。

### 资料
Plookup、logUp 论文（读构造节）；协议 §6.1 步骤 2、§6.3；docs/model.md §4、§9。

## B6 · OOD 采样与"绑定"（1 课）

### 目标
理解本协议最容易被误解的一环：接近 ≠ 唯一。掌握 OOD sample 如何在 list-decoding 区域钉死
唯一消息，以及它如何进入 commitment ID 支撑权重绑定。

### 讲义
**问题**：proximity test 允许 Johnson 半径的距离 ⇒ 球内可能有**多个**码字，编码**不同**的
消息。没有额外机制，作弊承诺者可以在两个码字之间"两面派"：验证者问 A 就以码字 A 解释，
问 B 就以 B 解释——承诺失去绑定。

**OOD sample**（协议 §5.5，原文级别掌握）：
- 每个被承诺的消息（除某步的掩码外，R12.10），验证者抽一个**多坐标扩域随机点**；
- 证明者回答**一个掩码元素**：消息的条目是某个 multilinear 多项式在 {0,1}^m 的值，回答 =
  该多项式在采样点的值；
- 结论："Except with small probability, all nearby codewords that fit the answer encode the same
  message, and every later step refers to that message."——附近的候选码字里，只有一个能同时
  满足 OOD 答案（MLP 在随机点取值一致 ⇒ 消息一致，概率 ~1−deg/|E|）。

**权重表的 OOD**：点由哈希表的根派生（不可由承诺者自选）；承诺者对每行发布一个掩码答案
（masked sums），放在 key file / leaf file。程序里叫 **record**（参数文件里 `record 1` 这行），
guide/terms 称 "OOD answers (masked sums of the weights), which every commitment publishes for
good"。这些答案**进入 commitment ID**（R4.9, R4.11：ID = hash(配置, anchor 根与形状, 掩码的
权重编码, OOD seeds 与 answers)）。

**绑定语义的三个层次**（guide/terms.md "Binding"，精确背下来）：
1. **index binding**：soundness 定理证明的——承诺时刻（含 committer 的哈希查询）固定了一组
   权重或"无"，之后被接受的输出是这组权重的模型输出；
2. **correctness of extraction**：提取出的权重就是放进去的权重——只对 Lean 写的两个承诺者
   证明（illustrative + compiled），**不对 cp_commit**；
3. **opening-form binding / no two openings**：承诺不能被"打开"成两组不同权重——同样只对
   Lean 承诺者（q/2^124 + 2^-100）。

**码定理的两个位置**（阶段 A 已埋伏笔，此处合流）：
- C++ 程序的打印界：**引用** ePrint 2025/2055 Thm 4.6，"the programs' accounting takes as
  given"，且"used with no bits to spare"（协议 §6.1、§6.4）；
- Lean 库：**不引用外部猜想**——"the coding theory it needs is proved inside the library, in
  files adapted from other formalizations, whose match to the published statements has not been
  independently compared"（what-is-proved.md）。两套界不同源，对比它们是 E1 的功课。

### 自测与答案要点
- **为什么 OOD 点用"哈希根"派生而不是链上挑战？** 承诺期的答案要**永久公开**（服务此后的
   所有批次），派生必须无歧义且不可被承诺者重试（重试=换根=换 ID）。
- **掩码在哪一层？** OOD 答案本身是权重信息，发出去必须加掩码（pad）；pads 的派生依赖秘密
   seed——这就是"seed 保密=历史答案全裸"的根源（C5/E2 会回到它）。
