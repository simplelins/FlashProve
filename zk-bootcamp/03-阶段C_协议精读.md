## C1 · 被证明的陈述：整数模型、请求与验收策略（1 课）

### 目标
把"一个证明到底声称什么"逐字吃透，包括 off-by-one、两种策略、以及"接受不等于什么"的负面清单。

### 讲义
**整数模型**（`docs/model.md`，两份实现：`integrations/vllm/integer_model/integer_model/model.py`
与 `lean/IntegerModel/Model.lean`；GPU prover 被测得与 model.py 在"哪些请求可证明 + greedy
选择"上一致——测试而非证明）：
- Llama 4 Maverick 文本 transformer 的**整数版**：定点激活 + 2 的幂 scales + 查找表实现
  非线性。关键形状：T=1024（窗口）、L=48 层、d=5120、n_h=40/n_g=8 头、dh=128、
  f=16384（稠密 FFN 宽）、fe=8192（每个专家宽）、NE=128 个路由专家、词表 V=202048。
  NE>0 时奇数层是 MoE、偶数层稠密。
- **权重**：整数矩阵，无 bias、norm 增益折进矩阵。key file 只证明：Emb 外的元素 ∈
  [−4096, 4095]；Emb 元素是四个带符号字节（base-256）。
- **scales（公开）**：`KL.bin` 存每层的右移 kq/kk/kv/ko/kg/ku/kd、两个 norm 的指数 M1/K1/M2/K2、
  softmax 移位 sh、rotary 开关 rp；MoE 层另有 kr/kgR/kuR。scales 公开而权重隐藏——注意
  这个信息边界（known-limits：scale file 甚至能"switch off model blocks"）。
- **非线性全走公开表**：rotary C/S 表、softmax 表 EX、SiLU 表 Ts、sigmoid 表 Sig，各自有
  参数文件里的 BLAKE2b 摘要（tsilu/tsig/trope/texp）。model.md §4 的 C(689,1) 例子说明：
  非正确舍入的数学库可能给出不同的表——所以表被摘要钉死。
- **MoE 路由**（model.md §7）：router 宽 logit lw → lr = 8·clamp(ly,2047)+l3；e* = argmax lr
  （并列取最小索引）；sc = Sig[lr[e*]] 乘在**路由专家的输入**上；共享专家 + 路由专家两路
  求和后一次移位。证明的是"路由计算正确"，但**激活了哪个专家对外隐藏**。
- **范围条件 1–8**（model.md §9）：Model 是**偏函数**——条件全满足才"有结果"。prover 用
  带符号字节 limb 写值（所以接受区间比"defined"窄：如 32639 vs 32767）。cp_commit 在承诺前
  用最坏情况界（`scales/worst-case-bounds.md`，"argued, not proved"）预判任何 prompt 能把
  值推到哪里。

**请求与范围**（协议 §2 + `guide/how-it-works.md`）：
- 请求 = T 个 token 的窗口（不足用填充，双方必须同填充）+ 范围 [r, e)；
- **位置 i 检查 token i+1**（off-by-one 是第一陷阱）。prompt P 个、回复 R 个：r = P−1、
  e = P+R−1 才覆盖全部回复。用"回复自己的位置"会漏掉第一个回复 token；
- 只在位置 T−1 ∈ 范围时，"下一个 token"才有意义（客户端自己提供）；
- top choice 并列时取**最小 token id**；logit gap 定义见 model.md §8（gap_t=0 当且仅当
  tok_{t+1} 是 argmax）。

**两种验收策略**：
- **exact match** = (C,θ,cap) = (256,256,0)：每个被检 token 都是整数模型 top-1。96 条存储的
  真实引擎回复（记分实验†）无一全对——所以服务实际用下面的策略；
- **clipped gap**：每 token cost = gap + 常数（cost exponent；注意 GAPS #12：C++ 验证器接受
  指数 7，Lean 只覆盖 8——又一个"两验证器不完全一致"实例），被检 token 的 cost 截到 C、
  允许 ≤ cap 个超 C、均值 ≤ θ。**参数松 ⇒ 接受≈什么都没说**；客户端必须用 `-policy` 声明
  自己期望的参数。源自 Token-DiFR（arXiv 2511.20621）温度 0 评分，仓库有四处改动。

**"接受不告诉你什么"**（协议 §3 的负面清单，逐条内化）：是谁的权重/模型好不好；范围外
token；整数模型与浮点模型多接近；回复是否完整（截断也算前缀）；权重是否真被隐藏
（`-public-weights` 无痕迹）；宽松策略下文本怎么来的。**你要自己供的五样东西**：ID、范围、
next token、策略参数、自建的验证器。

### 作业
1. 手算一个例子：prompt 5 tokens、reply 3 tokens、T=16。写出 r、e、每个被检位置检查的
   token、填充位置数。
2. 按 `guide/verify-a-proof.md` 构造自己的 `.req`（不要用证明附带文件！）并验证存储示例；
   再用错误范围（漏 1）重跑，观察输出差异。
3. 读 `docs/what-is-not-hidden.md` 全文，做一张"谁能学到什么"的表。
4. 读 `docs/model.md` §5–§8，把每层计算写成一句话流水账（norm→qkv→attention→Wo→FFN→residual）。

### 自测与答案要点
- **为什么证明对象必须是整数模型？** "正确"需要无误差余地的定义；浮点结果不可作为
  密码学陈述的精确谓词。
- **clipped gap 宽松时接受意味着什么？** 只意味着"被检 token 的成本共同满足客户端自己报的
  两个界"——协议原文："With loose bounds, acceptance therefore says little or nothing."
- **填充为什么双方必须一致？** 证明匹配"恰好一个请求"，换填充=另一个请求=另一个陈述。

### 资料
`docs/model.md`（全文）、协议 §1–§3、`guide/how-it-works.md`、`docs/glossary.md`。

## C2 · 承诺阶段：权重表、leaf table 与 commitment ID（1 课）

### 目标
把离线阶段走一遍：编码 → 范围证明 → 一次性测试 → leaf/link → ID；理解"磨损"与承诺生命期。

### 讲义
**四步流程**（协议 §4 + §6.1–§6.2）：
1. **Encode**：权重 → base-256 数字位 → 矩阵 M → 按块成行 → 加随机元素 → RS 编码 →
   权重表（anchor）→ 对列建 Merkle 树。
2. **Range proof**：lookup 证明所有数字位在固定小范围内、组装出的权重也在（Emb 只查数字位）。
   动机见 B5。
3. **One-time test**：对 anchor 跑一次"test on the table"（= 每批都跑的 shared+second chains
   这一对，参数与 label 不同）。**注意协议原文的精确性**："The two are not interchangeable,
   because a batch's test is sound only for a table that has already passed a first test"——
   一次性测试先建立"表接近码字"的事实，批处理测试才有意义。
4. **Copy（leaf table）**：同一权重用**新随机性**再编码若干份。每份的公开 leaf file 含
   **link proof**：折叠 anchor 与 leaf 的行（同一组随机因子）后证明两个折叠向量 (a) 各自
   符合自己表的打开列，(b) 在权重部分的随机点上一致。为什么够："different matrices give
   different folds for all but a small fraction of factors, and different folds disagree at almost
   every point"。link 也会开 anchor 的列 ⇒ leaf 数量受 anchor 的 query bound 限制，且
   **承诺后不能补加 leaf**（§6.2）——提供商必须在承诺时决定全生命期用量。

**commitment ID** = 64 位十六进制 = hash(三份配置文件, anchor 的根与形状, 掩码的权重编码,
OOD seeds 与 answers)（R4.9, R4.11）。三份配置 = `policy.txt`（参数）+ `KL.bin`（scales）+
`layout.txt`（布局）。**定理的边界**：ID 按设计覆盖配置，但 soundness 定理是"在给定公开
文件下"陈述的，并没有证明"同一 ID 不能在两组文件下验证"——所以客户端要**像持有 ID 一样
持有三份文件**（how-it-works.md）。

**磨损与生命期**：
- 每批开始：随机挑一个 leaf table → **先把将打开的列数写入磁盘计数器并确认落盘** → 才开列。
  一批"算数"与否与成功失败无关；
- 默认设置每 leaf 至多 688,127 批（程序记账）；cp_prove 每批前检查所有 leaf 的余量，任一
  不足即停（停止行为与挑中哪个表无关——细节见协议 §4）；
- 新承诺不能"修复"超限的表；对同一权重再承诺需要一组**程序不检查的条件**（独立 seed、
  权重预先固定、计数器不复用……协议 §4 "A new commitment"）。

**`-public-weights` 模式**：seed 来自文件、无新鲜随机性——什么都隐藏不了，且公开文件
**看不出**用了这个模式（协议 §7）。客户端无法区分。

### 作业
1. 读一个 `prover/examples/` 的参数文件（如 target_full_f2 相关），找出 leaf 数、每批请求数、
   batch 上限，估算"一次承诺能服务多少请求"。
2. 画出承诺阶段的文件产物图：`ivk/`（key.bin + leaf/<k>.bin）与 `isk/`（seed、计数器、
   各表一层哈希树）里各有什么；哪些公开、哪些保密（对照 guide/how-it-works "The files"）。
3. 一个思考题写成 200 字：为什么表本体不存储、每批从权重文件重算再与存储的树层级比对
   （协议 §4 步骤 1 括号里那句）？（提示：磁盘/内存量 vs 重算成本。）
4. 读 `docs/operators-duties.md` 的"A new commitment"与计数器义务。

### 自测与答案要点
- **link proof 为什么能证明两表同权重？** 折叠是随机的：不同矩阵 ⇒ 折叠向量不同（除小概率）；
  两个折叠向量一致（随机点检查）+ 各自符合自己表 ⇒ 码字解码到同一消息。
- **为什么批次算数不看成功与否？** 隐藏性要求"开列的次数"与内容无关地被计入预算——成功
  与否可被操纵，计数不能。

### 资料
协议 §4、§6.1、§6.2；`guide/how-it-works.md` "The files"；`docs/operators-duties.md`；
`docs/what-is-not-hidden.md`（record/masked sums 条目）。

## C3 · 证明五部分：first chain、slot、shared chain、second chain（2 课）

### 目标
逐字节理解一次在线证明的结构——这是全系统的核心设计，也是"整批共享一次开表"效率
奇迹的所在。

### 讲义
**批处理三步准备**（协议 §6.3 开头）：收集请求 → 随机挑 leaf table → **先计数后执行** →
对每个请求跑整数模型。

**证明文件五部分**（顺序固定）：
1. **header**：指名用的 leaf table；
2. **first chain**（请求私有）；
3. **slot**（在批树中的位置）；
4. **shared chain**（批内所有文件的这一段逐字节相同）；
5. **second chain**（请求私有）。

**first chain**：输入 = leaf 根与编号 + 请求摘要 + **请求逐字节**（tokens 与范围，R14.3）——
"证明别的请求"这条路被输入绑定堵死。过程：
- 模型按**段**切分（每段一个 sub-proof）；每段**承诺 trace**（中间值）；
- sumcheck（掩码版）+ lookup 把段方程归约成：关于已承诺对象的**线性声称** + 关于权重表的
  声称两类；请求 token 以公开值进入方程；
- 最后一段 = **输出头**：编码"被检 token 满足策略"+（若 T−1 被检）"下一 token 是 top-1"；
  next token 明文发送；
- **每段一个 range check（"smallness"）**：−1/0/1 因子 + 数字位 lookup ⇒ 段方程在整数意义
  下也成立（B5）；
- **段间传递**：折叠当前段承诺为短承诺带入下一段——**不需要保存全 trace**；
- 链尾：所有权重表声称打包成 **g·M·e + μ = v**（g[i]·M[i,j]·e[j] 求和；g、e、v 公开；μ 是链
  开头承诺的掩码的已知组合）；证明者承诺**请求向量 w = g·M**；链以 seal 结束。

**slot**：共享挑战必须等**所有**请求都固定自己的声称之后才能抽。解法：各请求的 seal 成为
一棵小盐树（**batch tree**）的叶子，根进入 shared chain 的输入。请求**随机占位**，未用槽位
放随机摘要——目的是不让 proof file 的字节泄露批大小与其他请求（批耗时仍然泄露大小）。
失败的请求保留自己的叶子（salted hash 覆盖它，协议 §6.3 slot 段）。

**shared chain**（效率核心）：问题——每个请求都有 w = g·M 要对表核验；逐请求开表会瞬间
烧光 query bound。解法——**验证者对所有请求采样同一个随机点**，固定公式把点变成每 j 一个
的因子 e*（e* [j] = 块因子 × 块内偏移因子——与权重表"一行=一块"的布局对应）。若某个 w ≠
g·M，则 w·e* ≠ g·(M·e*) 对几乎所有点成立（Schwartz–Zippel）⇒ **一个共享向量 M·e\* 服务所有
请求**。五步（协议原文编号）：
1. 按块因子折叠表的行，提交折叠向量；
2. 验证者采样位置，证明者开列（**全批唯一一次开 leaf table**）；
3. 每条开列 × 块因子 ⇒ 折叠向量的一条线性声称；折叠后的 OOD answers 再给一条；
4. 用块内偏移因子从折叠向量派生共享向量，提交（线性关系）；
5. proximity tests 证明对两个向量的全部线性声称。
链以 seal 结束。**shared chain + 某请求的 second chain 合称 "the test on the table"**。

**second chain**：输入 = 两条 seal。proximity test 证明两条方程：w·e + μ = v（first chain 的
声称）与 w·e* = g·(M·e*)（把请求绑到共享核验上）。

**发布与检查**（协议 §6.3 末）：
- cp_prove **不跑验证器**：先临时名写完、再"release"改名。所以 bug/硬件故障可以发布出
  cp_verify 拒绝甚至**含未掩码值**的响应 ⇒ **运营商义务**：前端的 `cp_verify` 必须在批内任何
  响应离开提供商之前全部通过（vLLM 集成就是这么做的，例外见 integrations/LIMITS.md）；
- 失败三分类：单请求失败（其余照常）/整批失败/秘密自检失败（必停服务）。

**为什么这是奇迹级的设计**（讨论课）：400B MoE 全量权重 ~103GB 级别的矩阵 M，每请求只
做一次"向量×矩阵"式的归约声称 g·M·e；整批共享一个开表事件；表的随机性预算只被消耗
O(1)/批 而不是 O(请求数)/批。

### 作业
1. 把协议 §6.3 的 shared chain 五步画成时序图，标出每步"谁算什么、验证者收到什么字节"。
2. 手推共享向量正确性：设 w ≠ gM，P[w·e* = g(M·e*)] ≤ ?（把差写成 e* 的多项式，用
   Schwartz–Zippel；注意 w·e* 与 g·(M·e*) 都是 e* 的多元线性式）。
3. 解释：为什么"共享挑战必须最后抽"是 batch tree 存在的全部理由？没有它会发生什么作弊？
4. 读 `examples/rejected-proofs/` 的 README 与目录，选三个被拒证明，对照协议 §6.4 的十组
   检查表说出违反哪组。

### 自测与答案要点
- **μ 是什么、为什么公开安全？** 已知掩码组合；掩码本身是承诺过的随机量，组合公开不泄
  w/M（论证见协议 §7 隐藏段与 C5）。
- **为什么 slot 随机占位？** 让文件字节不含"批大小/其他请求"信息；这是设计意图（协议原文
  "This is meant to keep the batch's size and the other requests out of a proof file's bytes"），
  耗时仍泄露大小——hidden 与 not-hidden 的边界要分清。
- **test on the table 为什么需要"先过一次初测"？** 批处理测试的健全性以"表接近码字"为前提；
  anchor 在承诺期建立这个前提，leaf 在 link proof 建立。

### 资料
协议 §6.3（本课主教材）；`docs/glossary.md`（sub-proof / batch / slot / seal）；
`integrations/LIMITS.md`；`prover/docs/ends-in-short.md`（运行如何结束）。

## C4 · 验证端：十组检查、target 与退出码（1 课）

### 目标
把 cp_verify 的全部检查结构化；掌握"target/accounting/proof of work"三者的关系；能专业地
报告一次验证。

### 讲义
**十组检查**（协议 §6.4 表格——背下结构与 format §13 的对应）：

| # | 检查 | 防什么 |
|---|---|---|
| 1 | 从配置+key file 重算 ID 并比对 | 换模型/策略/scales/表 |
| 2 | 大小、轮数、误差界**只从配置与验证器代码**取（R0.2） | 文件自带弱参数 |
| 3 | 文件唯一读法：无剩余字节、元素 < p | 一文件两读 |
| 4 | 每个挑战从链重算；PoW 全检 | 挑战自选 |
| 5 | 每条开列哈希回根（R7.10/7.14） | 承诺后换答案 |
| 6 | key file 的 range proof + one-time test；leaf 的 link proof | 溢出权重/无绑定表/假 leaf |
| 7 | 段：sumcheck/lookup/range check 全跟一遍 ⇒ 线性声称交下个 proximity test 结算 | 假计算/假 token/模 p 作弊 |
| 8 | OOD samples、proximity tests、test on the table | 远离码字/两读/指向别家权重 |
| 9 | seals、slot 叶、批树根重算并喂进下一条链 | 跨运行拼接 |
| 10 | next token 比对；请求与摘要进 first chain 输入 | 张冠李戴的请求 |

**target 与账目**：
- 参数文件给每轮设 target；验证器只接受**每轮**误差 ≤ 2^-128（误差由**验证器代码**算，含
  PoW 计数——永远不从文件读）；
- 默认设置全尺寸下：71 轮靠 PoW（20–32 bits）才达标；不含 PoW 最弱轮 96.23 bits；整批
  合并读数 126.21（含 PoW）/ 96.23；更悲观的读数 108.32 / 76.55（协议 §6.4 "The target"）；
- **341 个 closeness 轮全部依赖码定理**（C++ 侧"当作公理"、无余量）；324 轮距目标不足
  0.1 bit；
- 命令：`cp_verify -plan accounting <参数文件>` 打印这些账目；
- 一句话纪律（协议原文）："These figures are a calculation, not a security level, and no
  theorem is about the programs."

**退出码与末行**（`docs/verifying.md` + README 表）：
| exit | 末行 | 含义 |
|---|---|---|
| 0 | `YES` / `WITHIN LIMITS: …` | exact match 接受 / 宽松策略接受 |
| 1 | `NO: <name>` | 拒绝（或本地故障） |
| 5 | `NOT CHECKED: <name>` | 无裁决——仅 `internal-stage`、`internal-exception-parFor` 可重试**一次** |
| 14 | `NOT-A-VERIFICATION` | 调用本身非法 |
| 2/3/4/15 | — | 命令行/文件问题，无裁决 |
诚实证明也可能罕见地得到"无裁决"或拒绝——都按**不接受**处理。

**报告规范**（AGENTS.md）：exit code + 完整末行 + 所传 ID + `covered:` 行 + `commitment:` /
`proof of work:` / `result-v1` 三行。`YES` ≠ `WITHIN LIMITS`——末行区分，退出码不区分。

## C5 · 隐藏论证与不隐藏清单（1 课）

### 目标
掌握 ZK 论证的 simulator 范式在本文的具体形态；背下"故意不隐藏"清单；理解每请求 1 bit
与 lost-mask 这两个最重要的现实风险。

### 讲义
**simulator 范式**（协议 §7）：目标是——存在一个**从不看权重**的程序，仅凭：配置、客户端
请求与 next token、每请求能否被证明（served/refused）、批数与批内结构、以及（它自己回答的）
哈希查询，就能产出客户端收到的**一切**。注意三个不在覆盖内：耗时；多项请求的联合统计；
模拟器运行时间未建模。

**设计上的隐藏机制**（对应"为什么"）：
- 打开的权重表列：RS 随机尾巴 ⇒ query bound 内均匀随机（A3）；
- 只被哈希的东西：盐（A4）；
- 发送的值：掩码（sumcheck 掩码、掩码 OOD 答案、掩码折叠……）；
- **next token 例外：明文**——它本来就是"要被验证的输出"。

**每请求 1 bit**：回答要么带证明（served）要么"failed"（refused）——是否 served 取决于权重
（区间条件、结果是否匹配）。Lean 的 ZK 定理把这 1 bit **显式允许**："One bit per request is
revealed (served or refused) … over many requests these bits tell what the model answers, and
no statement bounds what they reveal together."（terms.md ZeroKnowledge 条）——多次请求可以
二分猜出模型的下一个 token，**无定理限制累积泄漏**。

**故意不隐藏**（`docs/what-is-not-hidden.md`，必背清单）：模型架构；量化 scales；每条回复
本身；请求成败；批处理时长（并因此决定谁与谁同批）；权重表的掩码 OOD 和（record，公开
即设计）；故障事件；`-public-weights` 模式的一切。

**lost-mask：头号现实风险**（limits.md "the main risk"）：验证器**不检查掩码是否存在**——
bug/硬件故障丢失掩码后，证明仍可能通过。程序只有部分秘密自检；cp_prove 也不在发布前
自验。所以有"前端先验"义务（C3）与运营商义务清单。

**OOD pads 的脆弱链**（协议 §7 "The OOD answers"）：每个答案只靠一个 pad 遮着；pad 由
ChaCha20 从秘密 seed + 32 新鲜字节派生 ⇒ seed 泄露 = 历史上所有答案可被"去掩码"；系统
随机源若重复（如镜像机二次启动）⇒ 两个承诺的公开文件给出**每行一条精确方程**，永久。
ChaCha20 不被攻破、开列数在预算内、seed 永秘——四个条件缺一不可。

### 作业
1. 把 `docs/what-is-not-hidden.md` 整理成"信息项 × 谁能看 × 攻击场景"三列表。
2. 设计并写出"1 bit 泄漏攻击"的攻击计划（不必实现）：给定黑盒服务，如何用 served/refused
   位二分出一个固定 prompt 的模型输出？估算请求数量级。
3. 抄写协议 §7 的 simulator 输入清单，标注每项"为什么必须给它"（不给 ⇒ 模拟器产出会与
   真实运行可区分）。
4. 读 `guide/weight-hiding.md` 与 limits.md "The biggest risks" 节，写 300 字："如果我是
   提供商，我上线前要检查的三件事"。

### 自测与答案要点
- **为什么 next token 可以明文？** 客户端本来就知道自己的回复；隐藏的对象是权重，不是
  输出。
- **为什么 ZK 定理"允许"那 1 bit？** served/refused 与请求可服务性有关，模拟器需要它才能
  产出一致的应答流；去掉它定理不真——这是诚实声明而非缺陷掩饰。
- **掩码丢了验证器会报错吗？** 不会——验证器根本不检查掩码存在性。
