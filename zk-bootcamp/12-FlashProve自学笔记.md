# FlashProve 自学笔记：从零到全懂

> 设计目标：一个没有任何 ZK 背景的人，按顺序读完这份笔记，就能理解 FlashProve 的每一个
> 核心概念，并能向别人清晰地讲解。每个概念 = 一个直觉 + 一个公式 + 在 FlashProve 里
> 的角色。不追求严格性——严格性在 `docs/protocol.md` 和 Lean 里。

---

## 第一部分：问题（3 分钟读完）

### 1.1 你要证明什么

AI 服务商运行一个大模型（Llama 4 Maverick，400B 参数）。你发一条消息，收到回复。你怎么知道：

- 服务商真的用了他宣称的那个模型？（而不是偷偷换了个便宜的小模型）
- 回复没有被篡改？

**传统方法**：让你自己也跑一遍模型——不可能，400B 参数你没这个算力。
**可信执行环境（TEE）**：信任硬件厂商——引入了新的信任假设。
**zkSNARK**：服务商附上一个**数学证明**，你用普通 CPU 几秒内验证——**不需要重跑模型，不需要信任任何人**。

### 1.2 要证明的陈述（一句话）

> "已承诺的权重 M，在你给的 prompt 上运行，产出的每个 token 都是 M 的 top-1 选择。"

关键词：**已承诺**（承诺 = 一个 64 位十六进制的哈希值，绑定了唯一的一组权重）；
**top-1**（greedy 解码：每步选概率最大的 token）。

## 第二部分：ZK 基础（每个概念：直觉 + 公式 + FlashProve 的角色）

### 2.1 有限域（Finite Field）

**直觉**：一个只做加减乘除的数字系统，所有结果都"绕回"到一个固定范围内。就像时钟：
11 点加 2 小时 = 1 点（模 12）。有限域用素数 p 做模——p = 2^64 − 2^32 + 1（Goldilocks 域）。

**为什么选这个 p**：
- p < 2^64 → 每个元素恰好一个 64-bit 寄存器
- 2^64 ≡ 2^32 − 1 (mod p) → 乘法的约减只需移位和加法，**不用除法**
- 在 GPU/CPU 上极快，FPGA 上更自然（64-bit 乘法器是标准单元）

**FlashProve 的角色**：所有算术（模型推理、sumcheck、编码）都在这个域上做。
模型权重被量化成小整数（4-bit）， activations 被量化成 12-bit——**这些整数直接嵌入域元素**。

**扩域 E = F[X]/(X³−2)**：为了安全性，随机挑战从 E（约 192 bit）抽，不从 F（64 bit）抽。
因为 sumcheck 的每轮误差 ~1/|E| ≈ 2^-192，远超安全目标 2^-128。

### 2.2 多项式与 Multilinear Extension (MLE)

**直觉**：把一张表（数组）变成一个**函数**。你有一张 2^n 行的表 t[]，你想把它当作
一个 n 变量多项式的求值表。MLE 就是最简单的这种多项式——每个变量最高次数 1。

**为什么用 MLE 而不是高次多项式**：
- sumcheck 对 MLE 只需 **n 轮**（每轮消一个变量），每轮消息只有一个域元素
- 高次多项式的 sumcheck 需要更多轮或更大的每轮消息
- MLE 求值可以在任意点做（不只 0/1），这是 sumcheck 的基础

**公式**：给定表 t（2^m 个元素，按二进制索引 b = b₁b₂…b_m），MLE 定义为：
```
M(x₁, x₂, ..., x_m) = Σ_{b ∈ {0,1}^m} t[b] · eq(x, b)
```

**在 FlashProve 里**：权重矩阵 M 的每个元素、模型推理的每个中间值、sumcheck 的
每个 witness——都被表示为 MLE。**承诺的对象就是这些 MLE 的求值表**。

### 2.3 eq() — 选择函数（sumcheck 的瑞士军刀）

**直觉**：eq(x, b) 回答一个问题："x 等于 b 吗？"等则 1，不等则 0。它是 MLE 的
构建积木——**把 eq 乘上一个表的元素，然后对 b 求和，就等于在点 x 处求 MLE**。

**单变量**：eq(x, b) = x·b + (1−x)(1−b)。当 x=b 时 = 1，否则 = 0。

**多变量**（这是 FlashProve 到处用的形式）：eq 是逐分量的乘积：
```
eq(x, b) = ∏_{i=1}^{m} [x_i · b_i + (1 − x_i)(1 − b_i)]
```

**关键性质**：
- 当 x ∈ {0,1}^m 时，eq(x, b) = 1 当且仅当 x = b，否则 = 0
- 当 x 是随机域元素时，eq(x, b) 是一个非零域元素——它"选择"表中第 b 行
- eq(x, y) = eq(y, x)（对称）
- eq(x, x) = 1（自己等于自己）

**在 FlashProve 里的角色**：**无处不在**。
- sumcheck 的每轮消息就是"把一个变量求和后的多项式"——等价于 eq 在那个变量上的折叠
- 权重声称 `<g(x) eq(ψ,·), M> = τ`——g 权重行，eq(ψ,·) 选择列
- spread() 把 eq(gamma, r) 作为折叠权重——把表的行随机组合成一行

**一句话**：eq 让你用**一个域元素**"指向"表中**任意一个位置**——这是 sumcheck 能
把指数级求和压缩成单个值的根本原因。

### 2.4 Sumcheck 协议（整个系统的发动机）

**问题**：你有一张巨大的表（百万级），想证明"所有元素的和等于 v"。验证者不可能
逐个加——太慢了。

**Sumcheck 的解法**：把 n 个变量的求和，逐变量消去。每轮：
1. 证明者发一个**单变量多项式** g_i(X)（次数 = 当前变量的次数）
2. 验证者检查 g_i(0) + g_i(1) = 上一轮的值
3. 验证者抽一个随机数 r_i，下一轮的值变为 g_i(r_i)
4. n 轮后，只剩一个值：f(r₁, r₂, ..., r_n)——验证者用 oracle 读取或传递给下一层

**为什么安全**：如果 Σ f(x) ≠ v，那么第一轮 g₁(0) + g₁(1) ≠ v（至少差 1）。
验证者抽随机 r₁，g₁(r₁) 有 ≥ 1/|E| 的概率暴露不一致。每一轮独立引入 1/|E| 的误差。
n 轮后误差 = n/|E|——对 |E| ≈ 2^192、n ≈ 20，误差 ≈ 2^-187。

**为什么高效**：
- 证明者的每轮消息 = 1 个域元素（不是 n 个）
- 验证者的检查 = 1 次加法 + 1 次随机采样
- **总通信量 = O(n)** 而不是 O(2^n)

**FlashProve 里的 sumcheck**（三个变体）：
| 变体 | 用途 | FlashProve 里的名字 |
|---|---|---|
| 标准sumcheck | 检查一个表的元素之和 | blocks/iop/psc.h |
| masked sumcheck | 同上 + 加掩码防泄露 | PSC 的 hide 模式 |
| batched sumcheck | 多个声称合成一个 | BATT block |

**FlashProve 里的角色**：**整个证明的主体计算**——把"模型计算正确"归约成
"权重表的线性关系成立"。模型有 48 层、128 专家、1024 token——每一层的每个
矩阵乘法的正确性，都通过 sumcheck 验证。

### 2.5 Reed–Solomon 编码（权重隐藏的基石）

**问题**：你要**承诺**权重但不泄露它。承诺需要满足：
1. **绑定**：承诺后不能换权重
2. **隐藏**：从承诺看不出权重是什么
3. **可开列**：验证者可以要求看表的一部分（打开若干列），且这部分足以验证计算

**RS 编码的解法**：把权重变成一个多项式的系数，然后在这个多项式上取**很多点**的值。
多的这些点就是"冗余"——它们让验证者可以在不看到全部数据的情况下检查一致性。

**FlashProve 的编码**（Def 4.2）：
```
Enc(f; τ) = Σ_{j<t} τ_j · φ^j + Σ_{j<ℓ} f_j · φ^{t+j}
```
- f = 消息（权重的数字位，ℓ ≈ 4×10^8 个）
- τ = 随机系数（t = 44,040,191 个）
- 在 |D| = 2^32 个点 φ 上求值
- 结果 = 一行 2^32 个域元素（一个"码字"）
- 2048 行组成"权重表"，按**列**建 Merkle 树

**隐藏性质**：任意 t 列（t = 44M 个随机尾巴）的值与权重**独立**（Theorem 6.3）——
因为多项式在 t 个点上的取值由 t 个随机系数决定，与消息无关。t+1 列开始泄露。

**这就是"磨损"的来源**：每次证明打开几列 → 预算消耗 → 预算用完后表不再隐藏 →
需要新副本（leaf table）。

**公式解读（一行一个直觉）**：
- `Σ τ_j φ^j`：这是"垫子"（padding）——随机的，让前 t 个求值点与权重无关
- `Σ f_j φ^{t+j}`：这是消息（权重）的贡献——从第 t+1 个系数开始
- 整体 = 一个 deg < ℓ+t 的多项式在点 φ 处的值

### 2.6 Merkle 树与 Fiat–Shamir

**Merkle 树**：对 2^32 列的每个列建一个叶子哈希，两两向上合并得根。承诺 = 根。
打开一列 = 叶子 + 兄弟路径（25 个哈希）→ 验证者重算到根，比对即知列没被换。

**盐（salt）**：每叶哈希前加 40 字节随机盐——防止离线暴力猜测未打开列的内容。

**Fiat–Shamir**：交互式协议中，验证者发挑战。要变成**非交互**（一个文件），
挑战 = H(之前所有消息)——证明者无法预知挑战，无法作弊。
**但**：证明者可以"重试"（grinding）——改一条消息重掷挑战，直到得到有利的值。
每次重试花一次哈希查询。FlashProve 加 **proof of work**（在采样位置的轮次前，
要求哈希输出的低 κ 位为 0，κ = 20/28/32）——把每次重试的成本提高 2^κ 倍。

**FlashProve 的链**：不是单条 FS 链，而是 **7 条**（key 文件 3 条 + leaf 文件 1 条
+ proof 文件 3 条），通过 seal（链尾摘要）和 binding tree 互相关联——防止跨运行拼接。

### 2.7 Lookup Argument（查表论证）

**问题**：模型有非线性函数（SiLU、sigmoid、softmax）——这些不是多项式，
不能用 sumcheck 直接证明。怎么办？

**解法**：把这些函数的输入-输出对**存成一张公开表**，然后证明"我查的每个值
都在这张表里，且查出来的结果就是我用的结果"。这就是 **lookup argument**。

**LogUp（FlashProve 用的变体）**：
- 对每个表元素 t，引入"重数" m_t（= 这个值在 witness 里出现了几次）
- 证明 Σ_{keys k} 1/(k − α) = Σ_{entries t} m_t / (t − α)（对随机 α）
- 用 **乘积树**（product tree）高效计算——避免 O(n²) 的直接求和

**在 FlashProve 里**：
- 模型的 4 张公开表（SiLU、sigmoid、rotary、softmax）各有 BLAKE2b 摘要
- 键 = 表的索引（如 SiLU 的 key = 256·gc + g0，16 位）
- **K3 = 查表的结果**（三字元素 E）
- 森林 = 多张表按树结构组织——支持批量 lookup

### 2.8 MSM vs 哈希承诺——关键设计选择

**传统 SNARK**（Groth16、Plonk 等）用**椭圆曲线点**做承诺：
- 承诺 C = Σ s_i · G_i（MSM = Multi-Scalar Multiplication）
- 需要**可信设置**（trusted setup ceremony）
- 验证需要**配对**（pairing）——昂贵的密码学运算
- 好处：证明尺寸小（~200B），验证快（几个配对 ~ms）

**FlashProve 的选择：纯哈希（hash-based），完全不用椭圆曲线**：
- 承诺 = Merkle 树的根（BLAKE2b 哈希）——**无可信设置**
- 验证 = 重算哈希路径——**CPU 秒级，无配对**
- 代价：证明更大（~19 MB vs ~200B），验证更慢（21 s vs ~ms）
- 收益：**后量子安全** + **无可信设置** + **GPU/FPGA/ASIC 友好**（哈希和域乘不需要椭圆曲线运算）

**为什么这个选择对 LLM 推理证明特别重要**：LLM 推理的计算量巨大（16B ops/token），
proof 系统的开销已经 93×——如果再加上椭圆曲线 MSM 的开销（MSM 占传统 SNARK
prover 时间的 70%+），系统完全不可用。纯哈希路线让证明开销主要来自**sumcheck
和查表**——这些正好是 LLM 计算本身的结构。

## 第三部分：FlashProve 核心设计

### 3.1 权重承诺——"把 400B 参数变成一张可以验证的表"

**步骤**：
1. 把所有权重写成 base-256 **数字位**（矩阵 M：3,076,096 行 × 2^18 列）
2. 按列切成 2,048 行（每行 = 一段连续的数字位 + 随机尾巴）
3. 每行做 RS 编码（加 44M 随机系数 → 2^32 个求值点）
4. 对表的**列**建 Merkle 树（每叶 = 2048 行在同一位置的值 + 40B 盐）
5. 发布：树的根 + **OOD answers**（每行一个掩码的和）

**为什么行 = "数字位块"而不是"权重的行"**：因为表格的行需要**等长**（才能按列
建 Merkle 树），而权重的行长短不一。数字位块让每行恰好 ℓ 个元素。

### 3.2 中心归约——`g·M·e + μ = v`

**这是整个系统最重要的一个公式。** 理解了它，就理解了 FlashProve 的核心。

**问题**：模型的一层做了 `y = x·W`（矩阵乘）。你想证明"y 确实等于 x·W"，
其中 W 是已承诺的权重。但 W 是 400B 参数——验证者不可能逐个检查。

**解法**：验证者抽两个随机向量 g（权重行的权重）和 e（列的权重），证明者计算：
```
v = ⟨g ⊗ eq(ψ,·), M⟩ + μ = Σ_i g[i] · Σ_j eq(ψ, j) · M[i][j] + μ
```

**直觉**：这相当于——
- **把整个矩阵 M 压缩成一个数** v
- 压缩的方式是随机的（g 和 e 是验证者的挑战）
- **如果 M 的任何一个元素错了，v 就会以 1−1/|E| 的概率暴露错误**

**为什么这就够了**：验证者不需要检查 W 的每个元素——只需要检查**一个随机线性
组合**。如果组合对了，那么（以高概率）矩阵本身就是对的。这就是 **sumcheck +
线性归约**的威力。

**μ 是什么**：掩码项——证明者承诺的随机值的线性组合。它的作用是**隐藏**
v 中的权重信息（零知识）。

### 3.3 批共享——"整批只开一次表"

**问题**：每个请求都需要对权重表做一次线性声称。如果每个请求独立开表，
表的磨损会非常快。

**解法**：**所有请求共享同一个随机点 ψ\***，从而共享一次表的折叠和开列。
- 每个请求先在自己的链上发 W_c = g_c^T M（在看到共享点之前）
- 然后整批共享链：折叠表 → 开列 → 发 Omega = M·eq(ψ*,·)
- 每个请求用 `<g_c, Omega> = W_c(ψ*)` 收尾

**效果**：表的磨损 = O(1)/批（不随请求数增长），**批 24 的吞吐是批 1 的 6.4×**。

### 3.4 段折叠——"不需要保存全 trace"

**问题**：全尺寸模型的 trace（中间值）很大——如果全部保存在 GPU 内存里，
batch 64 就要 80GB。

**解法**：把模型按**段**（segment，~2 层一段）切分，每段：
1. 提交 trace（中间值）为承诺
2. 用 sumcheck 验证这段计算正确
3. **折叠**段的承诺为短承诺，传入下一段

**效果**：证明者内存 = 一个段的 trace + 一个短承诺——不需要保存全部 48 层的 trace。

## 第五部分：为什么这么设计（对比其他 ZK 系统）

| 设计选择 | FlashProve | 传统 SNARK (Groth16/Plonk) | STARK |
|---|---|---|---|
| 承诺 | RS 码 + Merkle（哈希） | KZG（椭圆曲线 + pairing） | FRI（哈希） |
| 可信设置 | **不需要** | Groth16 需要 | 不需要 |
| 后量子 | ✓ | ✗ | ✓ |
| 证明大小 | ~19 MB | ~200 B | ~100 KB |
| 验证时间 | ~21 s（CPU） | ~ms | ~10 ms |
| 权重隐藏 | ✓（RS 随机尾巴 + 掩码） | ✗（除非额外处理） | ✗ |
| MSM | **无** | **有（prover 瓶颈）** | 无 |
| 查表 | LogUp + 乘积树 | Plookup/LogUp | 可选 |
| 模型缩放 | 400B MoE | 一般 ≤ 1M 参数 | 按系统 |

**FlashProve 的独特组合**：**唯一同时做到** 权重隐藏 + 400B 规模 + 无可信设置 + CPU 验证。
代价 = 大证明 + 慢验证——对 LLM 推理场景（服务商有 GPU，客户端有 CPU）是合理 trade-off。

## 第七部分：给别人讲解的 5 分钟话术

> "FlashProve 做的事是：让 AI 服务商**用数学方法证明**他给你的回复确实出自
> 他宣称的那个模型——而且不泄露模型的权重。
>
> 核心思路分三步：
>
> **第一步：承诺权重。** 把 400B 参数编码成一张巨大的表，用 Reed-Solomon 编码
> 加上随机冗余。对表的列建 Merkle 树。树根 + 一个哈希 = 承诺 ID。
> 随机冗余保证：你可以看表的少量列，但看不出权重本身。
>
> **第二步：证明推理正确。** 模型的每层计算（矩阵乘、attention、查表）都用
> **sumcheck 协议**验证。sumcheck 把'数十亿次乘加都做对了'这个问题，压缩成
> 验证者检查'几十个单变量多项式'——每个多项式一个域元素。
> 整个模型计算最终归约为**一个公式**：g·M·e + μ = v，其中 M 是权重表。
> 验证者只需要检查这个线性关系在随机点上成立。
>
> **第三步：客户端验证。** 客户端拿到证明文件（~19 MB），在 CPU 上 21 秒内
> 重算全部挑战和 Merkle 路径，检查每一步——不需要权重，不需要 GPU，不需要
> 信任服务商。
>
> 代价是证明者比直接推理慢 93 倍（H100 上 111 token/s vs vLLM 的万级 token/s）。
> 但这是**密码学证明的代价**，不是效率 bug——你用 93 倍的计算换来了数学上的
> 确定性。而 batch 共享（整批只开一次表）和段折叠（不需要保存全 trace）让
> 这个代价从'不可能'降到了'可接受'。"

## 第八部分：常见问题（FAQ）

**Q: 为什么不用 KZG 承诺（更小的证明）？**
A: KZG 需要可信设置（ceremony）和椭圆曲线配对。FlashProve 的设计哲学是
"无可信设置 + 后量子 + GPU/FPGA/ASIC 友好"——哈希和域乘在这些平台上
远比椭圆曲线运算高效。证明大（19MB vs 200B）但验证仍然是 CPU 秒级。

**Q: "磨损"是什么意思？为什么表会用完？**
A: 每次证明打开表的几列（给验证者看）。表编码里的随机尾巴保证 ≤ t 列
（44M）不泄露权重。但超过 t 列后，观察者有足够的方程可以解出权重。
所以每张表（副本）只能服务有限次证明（688,127 批）。这是**信息论限制**，
不是工程 bug。

**Q: 为什么激活量化成 12 bits？**
A: 12 bits 让激活值能放进 16 位有符号整数（-2048..2047），从而：
①能直接作为 lookup 表的索引（SiLU 表 64K 条目 = 16 位键空间）
②乘法 12×4=16 bits 不会溢出 32 位累加器
③比 8-bit 精度高（outlier 不容易被截断到零精度）

**Q: ZK 的"零知识"到底藏了什么？**
A: 隐藏的是**权重**（通过 RS 随机尾巴 + 掩码）和**激活值**（通过掩码
sumcheck）。**不隐藏**的是：回复本身（客户端已经知道）、模型架构、量化
scales、请求成败（每请求 1 bit）。时间侧信道不设防。

**Q: 67,383 轮是什么概念？**
A: 每轮 = 一次验证者消息（哈希出一个挑战）。这些轮分布在 7 条 FS 链上
（key 文件 3 条 + leaf 文件 1 条 + proof 文件 3 条）。每轮的误差 ≤ 2^-128
（含 PoW 计入）。总安全 ≈ q/2^124 + 2^-101（q = 哈希查询数）。
