## E1 · Lean 形式化：六定理与 soundness 定理（2 课）

### 目标
精确掌握"Lean 证明了什么、以什么条件、以什么数字、没证明什么"。这决定你对整个系统的
信任级别。

### 讲义（第一课：定理系统）
**六个顶层陈述**（`lean/VerifiableInference/Statements.lean`）：
`Sound`、`SoundAndBinding`、`SoundOpened`、`Complete`、`ZeroKnowledge`、
`CompleteSoundZeroKnowledge`。
对编译系统（`compile (flashProve setup)`）另有**六条线**（`lean/AtFullSide/Face/TheSixLines.lean`）：
`sound`、`soundAndBinding`、`completeOnCanServe`、`zeroKnowledgeOnCanServe`、
`refusedHandsOutNoProof`、`repliesFit`——这是库对"编译后的证明器+验证器"的目标陈述。

**soundness 定理**（`sound_of_verify_at`，Lean 验证器 `verify`）：
- 界：接受假陈述概率 ≤ 约 **16·(q+2^23)/2^128 ≈ q/2^124 + 2^-101**（q=对随机预言机的哈希
  查询数，承诺者与证明者合计；2^23 是验证器自身查询的固定配额）。注意措辞：**124 bits
  per query，不是 "128 bits"**；且这是"假接受概率的上界"，不是"某个接受为假的概率"；
- 条件（逐条背）：① exact match（且 **verify 自己不检查策略文件**——你查 C/θ/cap=
  256/256/0）；② 随机预言机模型（BLAKE2b + 假设独立的第二个固定哈希）；③ 配置文件在
  哈希函数被抽取**之前**固定（对真实哈希调参的提供者在陈述之外）；④ 全尺寸、单一证明
  格式（"admissible configuration"：8 个参数自由度 + Lean reader 接受的 scales）；⑤ 一次
  一个证明（N 个同时提交 ⇒ N 倍误差，按整体查询数计；逐个检查/分 session 无界）；
- "false" 的含义：**在提取器读出的权重处为假**——提取器是不保证可计算的固定函数，读的
  对象是承诺与**承诺者的**哈希查询（不必然是提供者的）；
- 配套：三个定理把**每轮**误差压到 2^-128（在 verify 自身的公开文件测试通过的文件上）；
  PoW 计入——不计则采样位置的轮次为 2^-96…2^-110（程序加总，非定理）。

**承诺侧定理**：对两个 **Lean 写的承诺者**（illustrative committer ≈ cp_commit 的一部分；
compiled committer = 从 Lean 证明器编译而来）证明：
- soundness with binding（opening form）：q/2^124 + 2^-100；
- extraction（2^48 查询预算内，提取器返还所放权重）：误差 ≈ 2^-155；
- **没有定理联系它们与 cp_commit**（仅在小尺寸做过值级比对）；"绑定"不蕴含"承诺里
  有权重"——提取器给"无"时一切接受都算假。

**completeness / zero-knowledge**：
- Completeness：对 Lean 诚实方，interactive（IOP）形式失败概率 ≤ 2^-41；编译后 ≤ 2^-40
  （含 PoW 搜索放弃等自身失败）。覆盖"served requests"（可服务且声称输出=模型输出）；
  模型无结果处**不语**。BLAKE2b 下 verify 接受任何东西只靠运行记录（"a verifier that
  rejects everything is sound too, with error 0"——`rejectAll_sound`）；
- Zero-knowledge：IOP 内对诚实验证者；编译后对任意（查询受限）验证者；单承诺/单 leaf
  table/单请求；**每请求显式允许 1 bit**（served/refused）；公开文件自身、时间均不覆盖；
  模拟器运行时间未建模；
- 另有"weights 满足最坏情况检查 ⇒ 每个良构请求恰有一个模型输出且诚实证明以 2^-40 接受"
  的定理（`theHonestPart_complete_where_some_worst_case_check_passes`）——但"没有任何真实
  模型的权重被证明满足该前提"（已知通过的是造出来的权重）。

### 讲义（第二课：信任的证据分层）
**证明靠什么**（what-is-proved "What the proof rests on"）：
- 只依赖 Lean 三个标准公理；**不假设任何编码猜想**——所需编码理论在库内自证（文件改编
  自其他形式化，与已发表陈述的对应**未经独立比对**）；
- 独立核验器（nanoda）在单独 pass 中接受了 `sound_of_verify_at` 及其下全部声明；六个线与
  completeness/ZK 等定理**不在**该 pass 内（部分 pass 无裁决，多因内存/时间）；pin 的
  Lean 版本**早于**已公开的 soundness bug 修复（LIMITS L45）；
- `verify` 的可执行形式由定理与 `verify` 绑定（56 号 gap 的定理，在所有公开文件、所有解析
  证明上，哈希答案 32 字节时）；`lean-verify` 命令在 Lean 内求值它——但它信任 Lean 求值
  器/编译器/运行时/助手库/驱动文件，**声明构造（commitment ID、prompt、output 的还原）
  的短函数无定理覆盖**（"Look first at four things" #4）。

**实验记录（[evaluated]/[tested] 层）**：
- 参考运行：47 个诚实全尺寸证明全部被 Lean 验证器接受；57 个说谎证明 0 个通过（54 拒
  +3 解析拒）；
- **41 个改动输入中 32 个被拒**；被接受的 9 个全部是"不改变声称"的改动（Merkle 路径中
  验证者不经过的条目被翻位）——**可塑性（malleability）不被声明**：接受不证明"就是这个
  文件"；
- 一处 4 配对改动：cp_verify 与（解析后进）verify **在 3 处分歧**（cp_verify 更严）；
- C++ 与 Lean 验证器的哈希调用 881,280/1,166,983 匹配，其余仅部分解释（GAPS 22）；
- 881,280 这类数字告诉你：两个验证器是"近似对齐"，不是逐位一致。

**"What it does not say" 清单**（THEOREM.md 1217 行起，13 条——E2 的骨架）：
1. 被证明的是 Lean 验证器，非程序；2. 条件清单（124/q，一次性）；3. 仅 exact match（宽松
策略下 Lean 只证"输出满足策略"）；4. "假/模型"的语义（提取器权重+整数程序；不保证是谁
的权重、多大多好）；5. 整数模型≠浮点模型（逼近度是测量不是证明）；6. 承诺绑定仅对 Lean
承诺者；7. completeness（全拒验证器 soundness=0 的陷阱）；8. 声称在定理外构造；9. blocks
库可被误用（closed.h 合约外）；10. 改动的存储表可被接受（声称仍真的场景，SO-15.7）；
11. 证明可塑；12. 两验证器近似非相同（cost exponent 7/8 之例）；13. C++ 打印位数=自记账
（128.00 含 PoW、96.23 不含、每批 64 再扣 ~6 bits）。
