## 0. 起点与终点

**起点**：zk 入门 —— 理解哈希、"承诺—挑战—响应"的基本范式即可，数学细节不预设。

**终点（四条验收标准）**：
1. 白板讲清协议主线：承诺 → 证明 → 验证，每一步防的是哪种作弊；

3. 列出 Lean 六定理证明了什么、没证明什么，并说出至少两个研究切入点；
4. 对比 DeepProve 与 FlashProve 的技术路线，写出有依据的批判性分析。

## 1. 项目事实卡（第一课材料，全部出自一手文档）

**是什么**：Anthropic 于 2026 年 11 月开源的 FlashProve v0.16.0（Apache 2.0），一个"可验证推理"
（provable inference / inference verification）系统：AI 提供商用 zkSNARK 证明"这条回复确实出自某个
已承诺的模型"，而不泄露权重。博客存档在 `provable-inference.md`。

**作者**（博客署名）：Roy Rinberg、Alex Allain（Anthropic）；Alessandro Chiesa、Giacomo Fenzi、
Guy Weissenberg（EPFL）；Miranda Christ（MIT）；Rahul Dalal、Ben Mayer（Anthropic Fellows 等）。
另有 VerInf 的 James Petrie 致谢。注意仓库自述是 **research artifact：不维护、不接受贡献**。

**三方协议**：

| 阶段 | 程序 | 执行者 | 作用 |
|---|---|---|---|
| Commit（离线，一次） | `cp_commit` | 提供商 GPU | 权重 → 隐藏编码的权重表 → Merkle 承诺，发布 64 位十六进制 **commitment ID** |
| Prove（在线，每批） | `cp_prove` | 提供商 GPU | 对每条回复生成证明："已承诺模型产生这些 token" |
| Verify | `cp_verify` | 客户端 CPU | 几秒内验证，无需权重 |

另有 **Lean 验证器 `verify`**（`lean/`、`tools/lean-verify/`）：可执行、被机器证明，是安全声明
的锚点。

**关键数字**（README / 博客 / `guide/performance.md`）：
- 模型：Llama 4 Maverick 400B MoE（48 层、128 个路由专家），4-bit 量化，1024-token 窗口；
- 单张 H100，prefill 证明速度约 110 tokens/s（24 请求/批），证明 ~19 MB / 1024-token 请求；
- 比 vLLM 跑同一推理慢约 70–95×；客户端 CPU 秒级验证。

**被证明的陈述**（`docs/protocol.md` §2，务必逐字理解）：
- 证明对象是**整数模型**（`docs/model.md`）：量化权重 + 整数运算，无浮点误差余地；
- 一个请求 = T 个 token 的窗口 + 检查范围 [r, e)；位置 i 检查 token i+1（注意 off-by-one！）；
- 三条断言：①所有中间值留在 lookup 表/范围内；②被检 token 满足验收策略（exact match 或 clipped gap）；③若最后一个位置被检查，下一 token 是模型 top-1。

**声明的安全边界**（贯穿全课程的核心意识）：
- Lean 证明的是「**Lean 版协议 + Lean 验证器 verify**」的 soundness（≈q/2^124 + 2^-101，随机预言机模型）、completeness、zero-knowledge——仅 exact match、单承诺、单请求，**不含批处理**；
- C++ `cp_verify`、CUDA `cp_commit`/`cp_prove` **没有任何定理**，只有测试对齐；
- 技术报告不公开（`docs/limits-all-rows.tsv` 行 HW-763），协议 §7 的两个论证"未经充分检查"。

**代码规模**（C++/CUDA 行数）：

| 目录 | 规模 | 内容 |
|---|---|---|
| `blocks/` | ~59k 行 | 共享证明库：field/hash/code/tree/chain/iop/…，纯 C++17 头文件（除 3 个 .cuh），CPU 参考实现 |
| `prover/` | ~103k 行 | `cp_commit` + `cp_prove`（CUDA，H100） |
| `verifier/` | ~9.3k 行 | `cp_verify`（C++，CPU） |
| `lean/` | Lean 4 | 形式化：六定理 + 可执行验证器 |
| `scales/` | Python | 量化校准（fit_scales.py、calibrate.py、worst_case.py…） |
| `toy/` | Python | mask 规则的独立 Python 复现（quick_start_test.py、mask_rules.py） |
| `integrations/` | Python | vLLM 前端 + `check_proof.py` 客户端封装 |
| `paper/` | PDF | 技术报告（协议的 Lean 形式描述 + 证明） |

## 2. 理论主线一页图（课程骨架）

整条协议就是一条不断**归约**的链。每一层课程对应一段：

```
最终断言： "被检查的 token 出自已承诺的整数模型"
   │  ① 模型分段（segments）：每段提交 trace（中间值）
   │     sumcheck + lookup 把"计算正确"归约掉
   ▼
若干线性断言：  g · M · e + μ = v      （g,e,v 公开，μ 是掩码组合）
   │  ② 整批共享设计：所有请求用同一随机点 e*，共享向量 M·e*
   │     → 整批只开一次权重表（磨损的关键）
   ▼
"已承诺的权重表接近某条 RS 码字，且打开的列与折叠一致"
   │  ③ proximity test：fold → code switching → base case
   │     + OOD 采样钉死唯一消息（list decoding 下有多个候选码字）
   ▼
对少数随机打开列的检查：Merkle 路径哈希 + 范围检查
   （"模 p 成立的方程在整数上也成立"——smallness/range check）
```

配套的**隐藏机制**（权重保密）与**绑定机制**（承诺不可换权重）是两条并行的论证线，
在阶段 C 合流。

## 3. 五阶段课程表（预计 10–14 周，可按你的节奏伸缩）

### 阶段 A：数学与编码基础（约 2 周，5 课）

| 课 | 主题 | 仓库对应 |
|---|---|---|
| A0 | 摸底自测 + 环境检查 + Route 1 跑通 | `verifier/build.sh`、`examples/accepted-proof/` |
| A1 | 有限域：模 p 算术；Goldilocks p=2^64−2^32+1；扩域 E=F[X]/(X³−c)（默认 c=2） | `blocks/field/` |
| A2 | 多项式与 multilinear：求值、行主序索引约定（bit 0 = 第一变量）、折叠运算 | `blocks/README.md` 规则 3 |
| A3 | Reed-Solomon 码：编码、最小距离 n−k+1、Singleton、list decoding、Johnson 半径；**隐藏性质**：任意 t 个编码值均匀随机（t = query bound）→ 权重隐藏的基石 | `blocks/code/`、`docs/protocol.md` §5.1 |
| A4 | 哈希与承诺：Merkle 树、salt、随机预言机模型、Fiat–Shamir hash chain、proof of work | `blocks/hash/`、`blocks/chain/`、协议 §5.6 |

**作业**：Python 手写 ①Goldilocks 域四则运算 ②RS 编码器（验证最小距离）③toy Merkle 树含 salt。
**验收**：推导 RS 最小距离；解释"query bound t"为什么是隐藏预算；解释 salt 防的是什么攻击。

### 阶段 B：证明系统原语（约 3 周，6 课）

| 课 | 主题 | 仓库对应 | 外部材料 |
|---|---|---|---|
| B1 | sumcheck 协议：完整数学 + soundness 误差 deg·|F|⁻¹ + 你自己的实现 | `blocks/iop/hp.h`（masked sumcheck 接口）、`vf_sumcheck_*.h` | Thaler 书 Ch4 |
| B2 | GKR 多层求值（对照 DeepProve 路线） | — | Thaler 书 Ch6 |
| B3 | IOP 形式化：oracle 证明、Merkle 承诺、round-by-round soundness | `blocks/iop/`、`blocks/tree/` | Thaler 书 Ch7；zk-learning MOOC |
| B4 | proximity test：fold → code switching → base case；FRI 家族对比；本协议用 Chiesa–Fenzi–Weissenberg (ePrint 2026/391) | `blocks/iop/`：fold.h、cs.h、base_case.h、foldeq.h | ePrint 2026/391；STARK 101 |
| B5 | lookup argument：证明"每个值都在公开表里"（范围检查/数字位检查的引擎） | `blocks/iop/lkp.h`、`vf_lookup_*.h` | Plookup、logUp 论文 |

**作业**：①toy sumcheck 实现（故意用错误挑战，验证被抓住）；②跑 `blocks/first_look.sh`；③读
`blocks/iop/` 三个块（fold.h、cs.h、lkp.h）画消息流图。
**验收**：白板推导 sumcheck soundness；说清 OOD sample 解决什么、为什么编码定理是全局信任根。

## 6. 纪律（出自 AGENTS.md，做实验时必须遵守）

- 永不用 sudo/chmod/chown/rm 绕过错误；绝不改源文件改变结果；
- 不构建 `prover/`，除非任务明确需要（测试会覆盖 `bin/` 下的程序）；
- commitment ID 只从可信渠道获取（存储示例除外）；
- 报告结果必须给：exit code + 完整末行 + 所传 commitment ID；
- `YES`/`WITHIN LIMITS` 只说明程序行为，不构成安全声明。
