## 1. 三十秒版

论文标题即定位：**《FlashProve: Hash-Based Proofs of LLM Inference at 400 Billion Parameters》**
（paper/paper.pdf，114 页）。让提供商对 Llama 4 Maverick 400B MoE（4-bit 量化）的每条回复
生成零知识证明"这出自已承诺的模型"，权重全程隐藏；客户端 CPU 约 21 秒验证 `[perf]`。
关键实测：单 H100 批 24 请求稳态 **111.23 ± 0.92 tokens/s**（项目自设目标 100 已通过）、
证明平均 **18.78 MB**、承诺约 **39 分钟**、比 vLLM prefill 慢 **93.0×**（对最高负载）/
**71.4×**（对同批 24 prefill）`[perf]`。

## 2. 角色与程序 `[arch]`

| 角色 | 程序 | 运行于 | 目录 |
|---|---|---|---|
| 提供商 | `cp_commit`（一次承诺） | 1×H100 | prover/ |
| 提供商 | `cp_prove`（逐批证明） | 1×H100 | prover/ |
| 提供商 | 前端 `proof_middleware.py`（未改 vLLM 内嵌中间件） | 模型服务器 | integrations/ |
| 客户端 | `cp_verify`（一证一调） | CPU | verifier/ |
| 客户端 | `check_proof.py`（封装+比对）、`lean-verify`（跑 Lean 可执行验证器） | CPU | integrations/、tools/ |

三个程序共享 `blocks/` 库。**根本不对称**：`cp_commit` 会把 cp_verify 内嵌编译并对自己的
产物先验证再落盘；`cp_prove` 既不运行也不含验证器代码——这就是"前端必须先验"义务的
代码层根源 `[arch, pREADME]`。

**源码词汇表** `[pREADME]`：sub-proof = `fork`；table holder = `keeper`；私有随机值 = `coin`；
请求向量 w = `W`；共享向量 M·e* = `Omega`；批树 = binding tree；范围检查 = `smallness` `[format 换名表]`。

## 3. 产物文件学 `[arch, format]`

**配置三件套**：`policy.txt`（参数+形状+验收策略）、`KL.bin`（量化 scales）、`layout.txt`
（布局）。产生顺序：`weight_sums/` 写校验和文件（**与权重同等保密**）+ 提供商手写两行的
`fold.txt` → `scales/` 工具拟合出 KL.bin 与最终 policy.txt → `prover/tools/pack_layout.py`
写 layout.txt `[arch 步骤 1]`。

**承诺产物**：公开 `ivk/`（key.bin = anchor 根+OOD answers+一次性证明；leaf/<k>.bin = 每张
leaf 表的根+OOD answers+link proof）+ 64 位十六进制 commitment ID；保密 `isk/`（seed、
计数器、各表一层哈希树；永不复制/恢复）。ID 的计算函数是 `published_id`，位于
`blocks/frame/heads.h`，cp_commit 与 cp_verify 双方调用 `[arch "The files"]`。
表本体不存盘：cp_prove 每批从权重文件重算所需部分，与存储的树层级比对 `[协议§4]`。

**请求产物**：`<name>.req`（T 窗口 + r、e）、`<name>.y`（next token 或 0）、`<name>.proof`、
失败的 `.failed`。**格式层的换名表** `[format/README]` 必备（读字节/读验证器输出时对照）：

| 协议页叫法 | 格式/代码叫法 |
|---|---|
| weight matrix | the committed matrix of the weights' digits (11.5) |
| weight table: anchor / leaf table | stored table: anchor / further table（`table`、`the first table`…） |
| query bound | 行的 random tail（R4.10） |
| range proof / one-time test | the one-time chain（item `ranges`）；key file 的 shared/second chains |
| range check | the smallness test；`work smallness` 行；输出里的 `smallness` |
| leaf file / link proof | entry（拒绝名里）；round `LINK` |
| request vector w / shared vector | W / Omega |
| batch tree / seal | binding tree / the seal of an earlier chain |
| next token | round `REPLY` |

**学协议的黄金材料** `[format]`：`docs/format/toys/1-product.md`（SEND+OOD、BAT、带隐藏
多项式的 sumcheck、FOLD+末段、CS+组 proximity test——数学与字节并呈）、`2-links.md`（段
框架）、`3-key-and-entry.md`（key file 范围证明、乘积树 lookup、对 M 的声称批组、committed
table 测试、leaf link）。外加 `format_rules.py`——纯标准库 Python 重写了格式的编码与轮次
并带已知答案，`read_key/read_entry/read_proof.py` 逐字节走文件。

## 4. 端到端流程（七步）`[arch]`

1. **Prepare**：见 §3 三件套产生顺序。
2. **Commit**：权重→权重表（anchor）→ 范围证明（lookup，Emb 只查数字位）→ 一次性测试
   （对 anchor 跑一次"test on the table"）→ `-M` 张 leaf 表各自以 link proof 绑回 anchor →
   公开文件写盘前 cp_verify 逐字节过一遍。
3. **Publish**：ID 必须先于 prompt、不经被查服务器交付——否则提供商可"看到题目再承诺一个
   能答对的模型"并诚实证明 `[arch 步骤 3]`。
4. **Serve**：两种模式。ordinary serving = 浮点引擎出文本，事后对 prompt+reply 做一次
   prefill 证明，配 clipped gap；integer serving = vLLM 挂整数模型插件（integrations/vllm/
   integer_model/），回复可按 exact match 证明。实测：插件下 48/48 条短回复证明并通过
   †；96 条存证回复（16-bit 与 FP8 各 96）无一全 token 精确匹配（记分†）`[perf]`。
5. **Prove**：批 1–64 请求，随机挑一张 leaf 表；**先把将开的列数写入磁盘计数器并确认落盘，
   才开列**。批内六步（`prover/prover/service.cuh` 顶部有权威注释）`[arch]`：收请求定序 →
   采 32 新鲜字节+seed+请求选表、计数、派生批密钥 → 逐 pass 证明（每 pass `-in-step` 个请求）
   → **两趟权重扫描完成开列**：第一趟按折叠点折行（折叠点在批内所有 first chain 结束后才
   采）→ 提交折叠行 → 采列位置 → 第二趟算列 `[arch "Why step 4 needs two passes"；消息顺序
   见 blocks/iop/lin.h 与 foldeq.h 顶部]` → 每请求暂存 proof/y 或 `.failed` → 全批统一改名
   （release）。
6. **Provider check**：前端对批内**每**条响应跑 cp_verify，全部通过才放行（批 24 约 94 s，
   单证 22.6 s，中间件 6 并发）`[perf]`。此检查不保证隐藏——掩码丢了它看不见 `[arch]`。
7. **Verify**：客户端自建 .req/.y，`-id` +（宽松策略时）`-policy`；exit 0 且末行 `YES`/`WITHIN
   LIMITS:` 才算接受；还要读 `proof of work:`、`commitment:` 行 `[arch 步骤 7, 协议§6.4]`。

## 5. 协议内核：三层结构（块级地图全部经头文件核实）

### 5.1 工具层 `[blocks/README]`
field（F=Goldilocks 2^64−2^32+1；E=F[X]/(X³−c)，默认 c=2）/ hash（BLAKE2b 规格实现）/
chain（FS 链+PoW；Binder 把参数与陈述写进首查询，`Public<T>` 无 getter）/ tree（完美二叉、
列+盐叶）/ code（=(length, message length, random tail)——query bound≈尾巴长）/ coins
（ChaCha20 派生）/ numbers（Plan：全轮次、种类、误差、PoW 的一览表）/ engine（CPU 与 GPU
同接口，GPU 版承诺逐位一致 `[pREADME engine/]`）/ frame / toy。

### 5.2 块层：blocks/iop/ 的 18 块（`[iop/*.h]` 全部头注释核实）

| 块 | 头文件自述（浓缩） | 协议角色 |
|---|---|---|
| SEND | 发 oracle 消息（主行+掩码行）；验证者回 OOD 采样种子（点 z、标量 β，皆在 E 中）；证明者对每条消息回一个线性形式值 | 钉死每条消息（OOD 采样本体） |
| BAT | J 条线性声称按挑战 x 合成一条（Σxⁱ·claim_i）；不发任何消息 | 声称批组 |
| SPLIT | 跨两组的声称用掩码 κ 拆成每 组一条；证明者发 share t' | 跨测试组拆分 |
| HP | sumcheck 的隐藏多项式 + `Weight`（一个变量怎么求和） | 掩码 sumcheck 的机件 |
| PSC | **掩码 sumcheck**：`(φ₁×..×φ_k)(S(X,F(X))) + masks = target` 归约为带公开目标的线性声称；掩码一致使用 ⇒ 不泄 witness；运行于 H = U + ε·(S′+T) | 段内方程归约 |
| LINE | 多线性映射 V 两半（末变量 0/1）的声称 → 一条（随机 ρ） | 段闭合/折半 |
| FOLD | 带隐藏多项式的 sumcheck：一行组（2^k 主行+掩码行）的一条声称 → 折叠单行（g₁..g_k）+新掩码的一条声称 | 行组折叠 |
| CS | code switch：SingleRows 在新码下重编码 → 新 oracle 消息 g + 开列声称；旧行退场 | 换码 |
| BASE | proximity test 收尾：末行掩码发送+比较；masking oracle g*（每输入行一条 Enc(M*,R*)） | 测试基例 |
| IOPP | 一组的完整 proximity test 组合器（BAT 汇总开放声称与 OOD 声称→…→BASE） | "interactive oracle proof of proximity" |
| REQ | 请求证明的框架：段链（每段闭合进下一段）+ 末尾一次 proximity test；跑在 first chain 上 | 五部分之 first chain 的骨架 |
| LKP | **乘积树 lookup**：键向量每项 ∈ 公开表；RNG 与 WF 都经它；cp_verify 的请求子证明用独立实现（vf_lookup_argument.h） | 范围证明/检查的引擎 |
| RNG | 近似范围检查：整数矩阵 Y（不发送）的打包项+reads（其他块用的加权部分和）；证明 \|entries\| < 2D（宽松界） | smallness |
| BATT | 对 M 的 J 条张量声称（各自列点）合批到新列点；M 不随证明发送 | g·M·e 声称的批组 |
| FOLDEQ | 对承诺表折叠的声称 → 对新 oracle 消息 G_u 的声称；表=Index（2^v 行、一码、Merkle 过列、超一切证明存在）；编码线性 ⇒ 折叠行=折叠码字 | 折叠权重表 |
| LIN | **整批共享一次折叠**证明批内每请求对 M 的一条线性声称（`<g_c(x) eq(ψ_c,·), M> + masks = τ_c`）；消息 W_c、G_u、Omega；以 proximity tests 收尾 | 五部分之 shared chain |
| MEMBER | 请求在 LIN 中的份额：pending claims →（J>1 时 BATT）→ 发 **W = gᵀM** → caller seal | first chain 尾→w 承诺 |
| LINK | 证明新承诺表与第一张表条目相同（anchor/leaf 术语在此定义） | 五部分外围：leaf 绑定 |

辅助头（非"块"）：summand.h、mask.h、single_rows.h、relation.h、context.h、message.h、
tensor.h，以及 **wf.h**（committer 的范围证明，经 LKP）`[iop/lkp.h]`。

### 5.3 协议层到块层的映射 `(推断→已由块功能强支持)`
- key file = 一次性链（WF 范围证明 + one-time test）+ 自己的 shared/second chains `[format 换名表]`
  ——3 条链 `[GAPS 术语节]`；
- leaf file = LINK + 折叠 + proximity `[协议§6.2]`；
- proof file 五部分 `[协议§6.3]`：header → **first chain = REQ 框架**（段链：每段 PSC sumcheck
  + LKP lookup + RNG smallness；LINE 闭合；末段=输出头）→ BATT/MEMBER 发 W=gᵀM → seal；
  **slot** = 批树（binding tree）；**shared chain = FOLDEQ+LIN+IOPP**（全批一次折叠、一次开列）
  → seal；**second chain** = 两方程的 proximity（w·e+μ=v 与 w·e*=g·(M·e*)）。
- 每文件 3 条 FS 链 ×（key 3 + leaf 1 + proof 3）= 全协议 7 条链 `[GAPS 术语节]`。

## 6. 整数模型与量化 `[model]`

- Model = Llama 4 Maverick 文本 transformer 的整数版：定点激活 + 2 的幂 scales + 查找表。
  形状：T=1024、L=48、d=5120、40/8 头、dh=128、f=16384、fe=8192、NE=128 专家、V=202048。
  NE>0 ⇒ 奇层 MoE、偶层稠密。无 bias，norm 增益折进矩阵。
- 权重范围（key file 只证到这）：Emb 外 ∈ [−4096,4095]；Emb = 四个带符号 base-256 字节。
- KL.bin：每层 7 个右移（q/k/v/o/g/u/d）+ 2 组 norm 指数 + softmax 移位 sh + rotary 开关 rp；
  MoE 层加 kr/kgR/kuR；另有 MF/KF 与三个 eps。
- 五张公开表（rotary C/S、softmax EX、SiLU Ts、sigmoid Sig），每个有 BLAKE2b 摘要钉进
  参数文件（tsilu/tsig/trope/texp）——model §4 用 C(689,1) 例子说明非正确舍入库会改表。
- MoE 路由：lw → lr=8·clamp(ly,2047)+l3 → e*=argmax lr（并列取最小索引）→ sc=Sig[lr[e*]]
  乘路由专家**输入**；共享专家+路由专家求和后一次移位。路由正确性被证明；激活了谁隐藏。
- 范围条件 1–8 定义 Model 的偏函数域；prover 的 limb 表示使接受域更窄（如 32639<32767）。
  cp_commit 的最坏情况界（scales/worst-case-bounds.md）是**论证非证明**。
- 与浮点模型的差距是**测量**不是证明：整数版 top-1 与 16-bit 模型在 **6.81%†** 位置不同
  `[perf]`——这就是 exact match 无法直接用于普通引擎文本、必须 clipped gap 的数据根源。

## 7. 安全与信任：一张分层地图 `[proved, THEOREM, GAPS, limits]`

**Lean 证明了**（全部在随机预言机模型、全尺寸、exact match）：
- `sound_of_verify_at`（对 Lean 验证器 `verify`）：假接受 ≤ q/2^124 + 2^-101；五条件（exact
  match 且 verify 不自查策略；ROM+第二固定哈希独立；配置先于哈希固定；单一格式/尺寸；
  单证明——N 证同批=N 倍）。
- 编译系统六条线（sound / soundAndBinding / completeOnCanServe / zeroKnowledgeOnCanServe /
  refusedHandsOutNoProof / repliesFit）+ 六顶层陈述（Statements.lean）。
- completeness ≤ 2^-40（编译后）/2^-41（IOP）；zero-knowledge 显式允许每请求 1 bit。
- 提取器语义：false = 在提取器读出的权重处为假；绑定/提取只对两个 Lean 承诺者
  （illustrative / compiled，2^48 预算内提取误差 ≈2^-155），**不涉及 cp_commit**。
- 编码理论**库内自证**（改编自其他形式化，与已发表陈述的对应未独立比对）；C++ 打印界才
  把 ePrint 2025/2055 Thm 4.6 当作公理（无余量：341 个 closeness 轮中 324 个距 2^-128 目标
  不足 0.1 bit；71 轮靠 PoW 达标；无 PoW 整体 96.23、含 PoW 126.21、最悲观 108.32/76.55）。
- 独立核验器 nanoda 在单独 pass 接受了 sound_of_verify_at 及其下全部声明；pin 的 Lean 早于
  已公开 soundness bug 修复 `[proved]`。

**没证明/已测出的事实**（精选）：
- 三程序无定理；两验证器"近似不相同"：哈希调用 881,280/1,166,983 匹配 `[GAPS 22]`；
  41 个改动输入 9 个被接受（均不改声称；Merkle 路径验证者不走的位置翻位）`[GAPS 66]`；
  4 配对改动中 3 处两验证器分歧（C++ 更严）`[THEOREM]`；cost exponent C++ 收 7、Lean 只证
  8 `[THEOREM]`；blocks/ 库绕过 `chain/closed.h` 合约可造假接受 `[GAPS 9→limits]`；
  改动存储表可过 C++ 验证器（SO-15.7，外部计数表明声称仍真）。
- **FS 的两条已知缺口**：next token 迟至输出头段前才进链（SO-50）；开列/盐/路径永不进
  首查询（SO-53）`[arch "Challenges"]`。
- 运行侧事实：参考运行 47 诚实全尺寸证明全被 Lean 验证器接受、57 说谎证明 0 通过
  `[THEOREM]`；timed runs 1,851 证 cp_verify 全收、249 个改动调用全拒 `[proved]`。
- 头号风险：**lost mask**（验证器不查掩码存在性）；派生随机性按字面不满足报告条件；
  1 bit 累积泄漏无界；时间侧信道无界；`-public-weights` 无痕（route 4 的 Maverick 公开权重
  就用它，seed 已发布 `[getting-started]`）。

**性能边界**：64/批在 80GB 卡上不可依赖——公开权重三次服务 GPU 用到 80,629/81,559 MiB；
合成权重 64/批全部 CUDA 调用失败（8 次）`[perf, 协议§6.3]`。

## 10. 十大新手陷阱

1. 位置 i 检查 token i+1（off-by-one）；
2. 权重表的行 ≠ 权重矩阵 M 的行（行=块）；
3. `YES` ≠ `WITHIN LIMITS`（看末行不是退出码）；
4. `WITHIN LIMITS` 松参数下≈无声明；
5. commitment ID 与三份配置文件要一起持有（定理不保 ID↔文件唯一性）；
6. `-public-weights` 公开文件无痕（maverick 路线即用它）；
7. 表会磨损且 leaf 不可后补——承诺时定终身；
8. 掩码丢失验证器不报错（前端先验是义务不是保险）；
9. "128 bits" 与程序打印位数都不是安全声明；Lean 的 124/查询 才是定理；
10. 证明可塑（9/41 改动被接受）——接受≠"就是这个字节流"。
